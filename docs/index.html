macotasu-agent-skills

証拠を集める者と、判定を下す者を分ける。

AI エージェント向けのレビュー知識・開発ワークフロー・文書化の型を配るマーケットプレイス。 既存のレビュー支援が コードの書き方 を見るのに対し、ここが扱うのは その差分がプロダクトとして満たすべき性質、そして 誰がそれを判定するのか という構造のほう。 その構造をどう書き残すか、までを含む。

収録

3系統ある。レビューは差分を見る知識と、その判定を下す司法。 ワークフローは開発の進め方そのもので、片方向に依存し合う。 文書化は独立していて、この仕組みと無関係にも使える。

レビュー — 差分を見る知識と、判定を下す司法

saas-review
5軸 · 24項目
マルチテナント SaaS に固有の観点。テナント境界とデータ分離 / 課金・プラン・使用量メータリング / 権限と監査ログ / データ保持・削除とマスキング / 個社要件の混入。 「型は綺麗でテストも通るが、他テナントのデータが見える」差分を止める。
needs — なし
architecture-review
3軸 · 14項目
事業形態に依存しない観点。DB と外部サービスの二重書き込み（outbox）・部分失敗・冪等性・ 順序保証 / API とスキーマの後方互換 / 観測性と障害時の運用。 見るのは「壊れないか・壊れたことを知れるか・止められるか」。
needs — なし
review-judge
1 agent
レビューの拘束力ある最終判定だけを下す司法。観点別の所見と決定性チェックを束ね、 4つの判定のいずれか1つを返す。Edit / Write を持たないので直せない。 下の2つが共に依存する共有基盤で、独立した配布単位にしてある。
needs — なし

ワークフロー — 開発の進め方

spec-intake
2 skills
立法の支援。issue での議論を、実装根拠になる仕様まで持ち上げる。 grill-issue が曖昧な issue を質問攻めで詰め、spec-draft が 完了基準と検証コマンドつきの仕様を起草して PR にする。承認は必ず人間。 自律ループを回さなくても単体で使える。
needs — grilling（外部・任意）
conductor
1 skill
開発の単一フロントドア＝指揮。フェーズを判定し、行政に実装させ、 書記に証拠を出させ、司法に持ち込む。自分ではコードを書かず、判定も出さない。 三権のどこにも属さない。
needs — dev-crew / review-judge / feature-dev / pr-review-toolkit / commit-commands
dev-crew
3 skills · 2 agents
行政（実務）。契約に沿って実装し、ビルド・型・lint・テストの決定性証拠を 揃えるところまで。司法を呼ぶ権限を持たず、合否も宣言しない — 証拠を揃えて指揮に返す。出荷・運用と書記の職能エージェントも同梱。
needs — feature-dev のみ
loop-engine
1 skill · 1 command · 2 scripts
人間が書いた仕様を起点に、拾い上げ→実装→司法検証→PR を回す自律ループ（HOTL）。 既定は報告のみ・副作用なし。実装まで進む設定でも 必ず PR で停止する——自動マージはしない。
needs — dev-crew / review-judge

文書化 — 構造と理由を書き残す

spec-page
1 skill
説明書・仕様書・設計文書を HTML 1枚にまとめる。収録物の一覧ではなく 対象の構造と、なぜそう決めたかを伝える形式に落とす。 配信環境で初めて出る欠陥（文字化け・横スクロール）を公開前チェックで潰す。 markdown で足りる内容は HTML にしない、という判断から始める。
needs — なし

全体像

issue での議論から PR のマージまで。横線より上が人間の意思決定、下が実行で、 この線が「issue は発見の場であって仕様ではない」という区別そのもの。 人間が止める点が2つあり、そこがこの仕組みの監督点になる。

人間が止める点は2つ。仕様の承認（②のマージ）と、最後の PR のマージ。 自律で回していても、この2点は必ず人間を通る。③ Spec: コメントと loop-ready ラベルの付与も人間が行う——仕様が main にマージされる前に ラベルが付くと、ループが存在しない仕様を指して落ちるため、代行させない。

役割の分離

上の図の横線から下を拡大したもの。観点を増やすことより、誰が何を できないようにするかのほうが効く。禁止を規約に書くのではなく、権限を与えないことで 構造的に強制する。

立法
人間が承認した goals/<slug>.md（起草は spec-intake が支援）
ボットは承認しない。書き換えもしない
行政
dev-crew:implement（＋公式 feature-dev）
司法を呼ぶ権限。合否も宣言しない
司法
review-judge:judge
Edit / Write ツール。直せない
指揮
conductor:dev（手動）／ loop-engine（自律）
コードを書かない。判定も出さない
書記
pr-review 6観点 ／ business-reviewer ／ domain-architect ／ saas-review ／ architecture-review
拘束力。所見を出すだけ

左が役、中央が担い手、右が「持たないもの」。分離を支えているのは右の列。 指揮だけが三権のどこにも属さず、手動なら人間が、自律なら loop-engine がその席に座る。

行政から判事へ直接の経路が無いのが要点。実装した主体は、自分の成果を判定に 出すかどうかを決められない。「これは軽微だから判定は不要」という判断自体が判定であり、 行政には属さない。同じ発想で判事は Edit / Write を持たない — 修正できてしまえば「実行と検証が同一主体」になり、独立性は書いてあるだけの建前になる。 直したくなったら差し戻しの理由に書く、それしかできない。

PASS

決定性チェックが全て緑で、証拠も揃っている。

RETRY

証拠が足りない。触った面に必要な証拠の型が欠けている。

REJECT

基準を満たしていない。理由を書いて実装側へ差し戻す。

ESCALATE

無人で判断してはいけない領域。人間に上げる。

チェックリストの書式

観点は全て固定の4フィールドで書く。形式が中身の質を決めるので、書式のほうを先に縛っている。

観点
何を見るか。例：課金イベントの冪等性
なぜ危険か
守らなかった時に実際に起きる事故。抽象的なリスクではない。 例：決済 webhook は at-least-once で再送される。重複排除が無ければ二重課金が起き、返金対応と信頼の損失が同時に発生する
どう検出するか
見るファイル・grep・実行コマンド。エージェントがそのまま実行できる形で書く。 例：grep -rn "idempotency|Idempotency-Key" と、webhook ハンドラに受信イベント ID の重複排除があるか
よくある間違った実装
実際に踏まれるパターン。 例：処理途中で例外が出ると 200 を返さず再送されるのに、「一度しか来ない」前提で副作用を先に実行している

「どう検出するか」が書けない項目は採用しない。 レビュー時に実行できない項目はチェックリストではなくポエムで、ノイズにしかならない。

依存関係

spec-intake 立法支援 依存 grilling（外部・任意）のみ dev-crew 行政 依存 公式 feature-dev のみ review-judge 司法 依存 なし conductor 指揮 必須 dev-crew / review-judge ＋ 公式 pr-review-toolkit / commit-commands 任意 frontend-design / code-simplifier / saas-review / architecture-review loop-engine 自律 必須 dev-crew / review-judge（自律モードでは loop-engine が指揮の席に座る）

行政から司法への矢印が無いのが要点。実装した主体は、自分の成果を判事に 持ち込む権限を持たない。「これは軽微だから判定は不要」という判断自体が判定であり、 行政には属さない。なおプラグインの仕様には依存を宣言する仕組みが無いため、 conductor は招集の前に前提プラグインの有無を自分で検査し、 欠けていれば導入を促して止まる。

Claude Code 以外で使う

中身は Agent Skills 形式の素の Markdown で、 特定のランタイムに依存する記述を本文に持たない。plugins/*/skills/*/ をそのままコピーするか、 checklists/*.md を任意のエージェントのコンテキストに渡せば使える。 プラグインとマーケットプレイスの仕組みだけが Claude Code 固有。

育て方

放っておけばチェックリストは書いた日が最終更新になる。何が追記を発火させるかを決めてある。

取りこぼしだけ書く

追記するのは「このパックに無かったせいで見逃しかけた観点」だけ。良い指摘を片端から足すと膨張し、かえって発火精度が落ちる。

初期の観点は裏付けを持たない

最初の軸は一般知識で書き起こしたもの。実際の PR に当てて空振りしたら直す前提でいる。以後に足される項目は上の規則により、その時点で実例を持っている。

一般化してから入れる

特定企業の内部事情・数値・固有のアーキテクチャは書かない。一般化した観点に落としてから入れる。

決定の記録

後から見て「なぜこうなっているのか」が分からなくなる決定だけを残す。結論ではなく理由のほうが価値がある。

レビュー観点を2つのプラグインに割った
境界は「マルチテナントで課金して継続提供する事業形態に固有か」。 outbox も後方互換も観測性も SaaS 固有ではないので architecture-review 側。 分けたのは利用者がまだ誰もいない時点——名前の変更は利用者の参照を壊すので、 分けるなら無料で済む時期しかなかった。
司法を独立したプラグインにした
当初は指揮役のプラグインに同梱していた。循環依存を避けるための消極的な配置だったが、 それだと行政が司法を配る形になり、分離を主張しながら梱包が主張と食い違う。 指揮も自律ループも判事なしに仕事を終えられず、 どちらも依存するが、どちらも所有していない。 判事が読む検証カタログも、プラグインを跨ぐとパスが解決できないので判事と同じ側に置いてある。
指揮と実務を分け、行政から司法を呼べなくした
当初はひとつのプラグインが、フェーズ判定・実装の委譲・書記の招集・司法への持ち込みを すべて兼ねていた。だがそれは実装した主体が、自分の成果を判定に出すかどうかを 決められるということで、「軽微だから判定は不要」という逃げ道が実際に規約に書かれていた。 判断自体が判定なので、行政には属さない。 いまは行政（実装と自己検査）・司法（判定）・ 指揮（誰に何をさせ、いつ司法に持ち込むか）に分かれ、 指揮の席には手動なら人間が、自律なら loop-engine が座る。
退会時の削除はマスキングでもよい
取引記録に保持義務がある場合、行ごと消すと会計・監査が壊れる。 レコードは残して個人情報だけ不可逆に落とすのが正解。 危険なのは手段の選択ではなく、マスキングが可逆（対応表や元値が残っている）であること、 および自社 DB だけ処理して外部サービスに原本が残ること。
第三者のスキルを同梱しない
grill-issue が依存する grilling は外部由来（MIT）。 再配布は許されるが、上流の更新追従の責任を背負うことになる。 パスで読む代わりにスキル名で invoke し、無ければその旨を告げて続行する形にした。
設定ファイルはプラグイン側に置かない
プラグインの実体はインストール先のキャッシュで、読み取り専用として扱うべき場所。 ユーザー設定は使う側のリポジトリに置く（例: .claude/release-note.config.yaml）。
ループの状態をファイルではなく GitHub に置く
定期発火を cloud で回すと、毎回まっさらな clone から始まるので、作業ツリーに書いた状態は 次の発火に残らない。着手ロックとエスカレーションは issue のラベルが持つ。 副次的に、ボットがリポジトリへ状態を書き込む必要がなくなり、push 権限を PR ブランチだけに 絞れる。Watching にラベルを与えないのは、PR の存在が既に GitHub 上の事実で、 ラベルで二重に持つと必ずズレるため。
試行回数は保存しない
判事に3回差し戻されたら人間に上げる、という上限は残っている。だが 1回の発火が終わると、その issue はどの経路でも走査から除外される （3回使い切り＝escalated ラベル／PR 作成＝Closes #N の open PR が存在／ 途中終了＝ロックが残る）。次の発火で拾い直さない以上、前回の回数を持ち越す相手がいない。 状態をラベルに移した副産物として、カウンタの永続化そのものが不要になった。
止まったロックは自動で解除しない
発火が途中で死ぬとロックのラベルが残り、その issue は二度と拾われず静かに止まる。 一定時間を超えたものは検出して報告するが、ループはロックを取り直さない — 落ちた原因が残っているかもしれず、死んだ実行がブランチや PR を作りかけていれば自動再開は 二重作業になる。報告には残骸（ブランチ・PR・経過時間）を添えて、人間が後始末できるようにする。 ルールは一行: ラベルを外せるのは、正常完了したループと人間だけ。
定期発火は cloud routine で行い、手元の繰り返し実行はやめた
セッションが起きている間しか回らないという制約が、自律ループの前提と噛み合わない。 ただし routine の定義は claude.ai アカウント側に保存され git に残らないので、 routine に置くのは「同梱の手順書を読んで従え」という3行のポインタだけにして、 実質的な手順はプラグイン側（＝版管理下）に残している。
モデルの使い分けはプラグイン側に持つ
どの職能をどのモデルで動かすかはコスト判断なので個人設定に置く、と一度は決めた。 だが利用者のホームディレクトリにある指示書は cloud session に届かず、 無人実行でこそ効いてほしいコスト制御が、そこでだけ適用されないという逆転が起きる。
初版を公開するまでバージョンを上げない
誰も参照していない間のバージョン更新は情報を持たない。 構築中は 0.1.0 のまま据え置き、公開後から semver を回す （観点の追加＝minor / 文言修正＝patch / 名前・構造の変更＝major）。
