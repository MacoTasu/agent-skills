# 規範 (Rule / SSOT) — ループ取り込みトリアージと仕様の秩序

> 人間が承認した standing な規範（守るもの）。トリガ対象外。司法・`/conductor:dev`・`/loop-engine:loop-engine` が参照する。
> 「**全部を仕様駆動にしない**。自律ループに入れる仕事を選択的に絞る」ための線引き。

## 意図 (なぜこの規範が要るか)

- 仕様駆動は**無人ループ (`/loop-engine:loop-engine`) の検証アンカー**としては必須だが、全タスクに課すと
  「typo に仕様一式」のように割に合わず、仕様化できない仕事に**偽の仕様**を生む。
- どの仕事をループに入れ、どれを `/conductor:dev`／人間駆動に回すかの基準を明文化し、
  「迷ったら全部仕様化」への暴走と、逆に「未仕様の仕事をループに流す」事故の両方を防ぐ。

## 規範 (守ること)

### 0. 仕様は spec-kit の Living Spec — 1つの `spec.md` が「今の振る舞い」と「契約」を兼ねる【最重要】

| 何 | 場所 | 所有 | 変え方 |
|---|---|---|---|
| **機能の仕様**（その機能が今どう振る舞うべきか） | `specs/<機能>/spec.md`（`plan.md` / `tasks.md` は派生） | 人間（承認＝仕様の PR のマージ） | 振る舞いを変えるなら、**実装より先に** `spec.md` を直す仕様の PR |
| **原則**（全機能が守ること） | `.specify/memory/constitution.md` | 人間 | constitution の PR |

- **仕様を先に PR にする。** 人間がマージして承認してから実装する。実装 PR は `spec.md`・`plan.md`・constitution を
  変えない（変えれば司法が ESCALATE）。これで「コードと仕様が食い違う（仕様が腐る）」状態を作らない。
- 以前は「製品仕様（`docs/specs/`）」と「変更の単位（`goals/`）」を2層に分け、実装 PR で前者を追従させていた。
  Living Spec では `spec.md` がその両方を兼ねるので、2層の区別と追従の規律は不要になった。
- 仕様どうし・仕様と constitution が矛盾するなら **ESCALATE**（実装の根拠が無い）。

### 1. 3トリアージ — 仕事の行き先

| 区分 | 入口 | 仕様 |
|---|---|---|
| 無人化可能（検証可・境界明確・安全） | **`/loop-engine:loop-engine`** | **spec-kit の仕様一式（`spec.md`・`plan.md`・`tasks.md`）が main にマージ済み**（＝狭い少数派） |
| 人間が見ていれば足りる大多数 | **`/conductor:dev`**（human-in-loop） | 機能追加・振る舞いの変更は親が spec-kit で仕様を作る。小さな変更は仕様なし（インライン契約） |
| 探索的・曖昧・判断重・blast radius 大 | 人間駆動 | 書くと嘘になる。書かない |

- 仕様の合格ラインは "perfect" ではなく **"各基準を自動テストで二値判定できる" かつ "スコープと constitution で境界づけられている"**。
- 仕様の矛盾・欠落は**必ず ESCALATE**。security・課金・破壊的変更・認証認可は loop に入れてよいが、PR 本文で申告させる（`autonomy-gates.md`「要注意の変更」）。

### 2. issue は intake であって SSOT ではない（＝発見経路であり、仕様ではない）

```
issue / 観測 (起票・議論の場・可変・非バージョン)
   │  ← promotion: 人間が「やる」と決めた時点で仕様を書いて承認
   ▼
specs/<機能>/ (立法・versioned・仕様の PR で承認・基準はテストで判定)  ← 実装根拠はここだけ
   ▲
   │  ← Spec: コメント + loop-ready label が issue から仕様を指す（ポインタ）
issue #N ── /loop-engine:loop-engine <N> ──▶ 司法 → PR (Closes #N) 停止 (HOTL)
```

- **実装根拠（SSOT）は常に main にマージ済みの `specs/<機能>/`**。**issue の本文・議論から仕様を推測して
  実装しない**。issue が担うのは「どの仕様を今回実装するか」を指す**ポインタと意思表示**だけ。
- **昇格プロトコル（人間が行う）**: ① issue で議論する（`/spec-intake:grill-issue [番号]` で詰められる）→
  ② 「やる」と決まったら spec-kit で仕様を書いて仕様の PR → main マージ →
  ③ issue に固定書式コメント `Spec: specs/<機能>/` を投稿 → ④ **`loop-ready` label** を付ける。
  - **② は `/spec-intake:spec-draft <issue番号>` か `/conductor:dev` の親で起草できる**（PR で提案。承認＝マージは人間）。
    **③④ は代行しない**（仕様が main にマージされる前に label が付くと、ループが main に無い仕様を指して落ちるため）。
  - **仕様は「やる」と決めた瞬間に書く**（起票時ではない）。やらなくなった提案に仕様を書かせない。
  - コメント（本文編集ではなく）に書くのは、**いつ昇格したかが履歴に残る**ため。
- **起動経路**（どれも実装根拠は `specs/<機能>/`）:

  | 経路 | 入口 | 拾う対象 |
  |---|---|---|
  | 機能を直接指定 | `/loop-engine:loop-engine <機能>` | `specs/<機能>/` |
  | issue 経由 | `/loop-engine:loop-engine <issue番号>` | label + `Spec:` コメントで解決した仕様 |
  | 自動走査 | **cloud routine**（autonomous-entry） | **`loop-ready` label が付いた open issue**（`Spec:` コメントで解決） |

- **`loop-ready` label が無い issue は実装しない**。label があっても `Spec:` コメントで仕様に解決できない、
  仕様が main に無い、既に `Closes #N` の open PR がある、のいずれかなら **ESCALATE**。
- **起動の権威は issue 側（label と `Spec:` コメント）だけ**。仕様の PR の本文に issue 番号が書いてあっても、
  それを根拠に起動しない（人間の実行意思の確認点を迂回させない）。
- **ループが使うラベルは3つ**。`loop-ready`（人間が付ける GO）/ `loop-running`（ループが着手時に付ける
  ロック）/ `loop-escalated`（人間対応待ち）。**ラベルを外せるのは G5 正常完了時のループと人間だけ**。

### 3. バグ修正の仕様化 — 再現テストを受け入れシナリオにする

| バグの状態 | 行き先 |
|---|---|
| 原因判明・再現テストが書ける | **薄いバグ修正の仕様 → loop**（受け入れシナリオ＝再現手順と期待値。テストが red→green） |
| 原因不明・要調査（探索的） | **`/conductor:dev`／人間駆動**。再現可能になって初めて仕様化 |
| 1箇所の明らかな修正 | 仕様を作らず `/conductor:dev`（インライン契約） |

- バグ修正の仕様は薄くてよい: 1つのユーザーストーリーと、再現手順を Given/When/Then にした受け入れシナリオ、
  スコープ（修正のみ）。`tasks.md` は再現テスト→修正の順。

### 4. 仕様ディレクトリの命名と秩序

- **命名 = spec-kit のタイムスタンプ方式** `specs/<YYYYMMDD-HHMMSS>-<短い名前>/`
  （`.specify/init-options.json` の `feature_numbering: "timestamp"`）。
  - 理由: 並行して開いた仕様の PR が連番を取り合わない。作成順に並ぶ。
- **秩序 = フラット**。状態の項目は持たない。「承認済み」は main にマージされていること、
  「実装済み」は `Spec: specs/<機能>/` を持つ実装 PR がマージされていることで表す（事実から導く）。

## enforcement (どう守らせるか)

- `/loop-engine:loop-engine` は本規範の 2 に従い、**実装根拠を main にマージ済みの `specs/<機能>/` に限る**。
  issue 経由の起動は仕様への解決を必須とし、解決できなければ ESCALATE する。
- 司法 `review-judge:judge` は、各基準に対応するテストがあるか、実装 PR が正典を変えていないか、
  要注意の変更が PR 本文で申告されているかを採点観点に含める。

## 適用範囲 / 例外

- 適用: 自律ループの運用全般、および本基盤を配布した先のリポジトリ。
- 例外: `/conductor:dev` の小さな変更は仕様の要件の対象外（human-in-loop で人間が検証者のため）。
