# implement — 行政（実務）

**実装し、自分の仕事の証拠を揃えるところまで。** ここから先（誰に見せるか、合格か）は担わない。

## 職責の境界（最重要）

| やること | やらないこと |
|---|---|
| 合意済みの契約に沿って実装する | **フェーズ判定・職能の招集**（＝指揮の仕事） |
| 契約の範囲で作業ブランチ上に差分を作る | **司法を呼ぶこと**（持ち込むのは指揮） |
| ビルド・型・lint・テストを走らせ、結果を証拠として残す | **合否の宣言**（判定は `review-judge:judge`） |
| spec-kit の `tasks.md` に進捗（`[X]`）を記録する | **正典の変更**（`spec.md`・constitution は人間の所有物） |

**自己レビューはする。合否の宣言だけをしない。** 差分の読み返し、テスト・型・lint の実行、
`/speckit-converge` での作り残しの点検は、行政の仕事そのもの（先に自分で見つけて直すほど、差し戻しが減る）。
しないのは、その結果を**判定として扱う**こと。「テストが通ったので完了」は拘束力のある判定ではない。
自己レビューの結果は**事実と証拠として**返し、合否は分離した主体（司法）が出す。

## 契約は2種類

| 契約 | いつ | 完了基準 |
|---|---|---|
| **spec-kit の機能ディレクトリ** `specs/<番号-機能名>/` | 仕様の PR が人間にマージされた機能 | `spec.md` の `FR-###`・受け入れシナリオ・実装で満たせる `SC-###`。作業の順序は `tasks.md` |
| **インライン契約** | 仕様を作らない小さな変更（`/conductor:dev` の Plan Mode 合意） | 合意に書かれた各基準と、併記された検証方法 |

## spec-kit 契約では `/speckit-implement` を枠の中で使う

コードを書く部分は spec-kit の `/speckit-implement` に任せ、**その前後をこのスキルが受け持つ**。
書く手順は spec-kit のレールに乗り（上流の改善をそのまま受け取る）、三権分立に要る部分は枠が守る。

| | 担当 | 何をするか |
|---|---|---|
| 前の確認 | このスキル | 仕様が確定しているか・拡張フックの有無・作業前の状態の記録 |
| **書く** | **`/speckit-implement`** | `tasks.md` の順に実装し `[X]` を付ける |
| 後の確認 | このスキル | 範囲外の変更の検出・自己レビュー・作り残しの点検・証拠表 |

**`/speckit-implement` を枠の外で直接呼ばない。** 前後の確認が無いと、次が素通りする:

- `checklists/` に未チェックがあると人間に yes/no を聞いて止まる（前の確認で先に差し戻すので、枠の中では起きない）
- 技術スタックを検出して ignore ファイル（`.gitignore` など）に**足りないパターンを追記・無ければ作成**する。
  `.vscode/` や `.idea/` を追記することがあり、それらをコミットしているリポジトリでは害になる（後の確認で見つける）
- 要件ごとの証拠を返さない（後の確認で作る）

最後に自分で完了を検証する手順は良い自己レビューとして活かす。ただしその「完了」は判定ではない。

## 手順（spec-kit 契約）

1. **場所を確認する** — 作業ディレクトリが機能用のブランチ（または worktree）であること。
   `main` の上なら着手せず指揮に返す。spec-kit のスクリプトが機能を特定できるよう、
   `SPECIFY_FEATURE_DIRECTORY` が `specs/<番号-機能名>` を指しているか、`.specify/feature.json` がそれを指していること。
2. **前の確認** — `spec.md`、`plan.md`、`tasks.md`、あれば `data-model.md` / `contracts/` /
   `quickstart.md` / `research.md`、`.specify/memory/constitution.md` を読む。
   次のどれかに当たれば**着手せず指揮に差し戻す**（推測で補わない）:
   - `spec.md` に `[NEEDS CLARIFICATION: …]` が残っている
   - `checklists/` に未チェックの項目がある（`/speckit-implement` が人間に yes/no を聞いて止まる条件。先に返す）
   - `tasks.md` が無い、または `spec.md` の基準に対応するタスク（特にテストのタスク）が見当たらない
   あわせて:
   - **拡張フックを確認する** — `.specify/extensions.yml` に `before_implement` / `after_implement` の
     フックがあれば、何が走るか（自動コミット・push など）を把握する。コミット・push・PR 作成を行う
     フックが必須（`optional: false`）なら、指揮の出荷の手順とぶつかるので**着手せず指揮に返す**。
   - **作業前の状態を記録する** — `git status --porcelain` と `git rev-parse HEAD` を控える（後の確認で差分の出どころを判別するため）。
3. **書く** — `/speckit-implement` を実行する。spec-kit の手順どおり `tasks.md` の順（テスト先行）に実装し、`[X]` を付ける。
   実行中に仕様の誤り・不足に気づいた、または `spec.md` / `plan.md` / constitution を変えないと進めない状況になったら、
   **止まって指揮に返す**（振る舞いを変えるなら先に仕様の PR）。
4. **後の確認: 範囲外の変更** — 作業前の状態と比べて、変わったファイルを一覧にする。
   - `spec.md` と `.specify/memory/constitution.md` が変わっていたら元に戻し、指揮に報告する（正典は変えない）。
   - **ignore ファイル**（`.gitignore` / `.dockerignore` / `.npmignore` / `.eslintignore` / `.prettierignore` など）が、
     `tasks.md` のタスクに無いのに変わっていたら、**この実行で加わった変更だけを元に戻し**（この実行で新規作成されたものは削除し）、
     何を戻したかを報告する。元から存在した内容には触れない。
   - それ以外で `tasks.md` のタスクが指すファイル・`plan.md` の構成から外れる変更があれば、「スコープ外に触れた点」として報告する。
5. **後の確認: 自己レビュー** — 差分を読み返し、テスト・型・lint を実行する。直せるものは直す（自分の仕事の範囲で）。
6. **後の確認: 作り残しの点検（最大3回）** — `/speckit-converge` を実行する。仕様・計画・タスクとコードを突き合わせ、
   作り残しを `tasks.md` に **Convergence フェーズとして追記するだけ**の点検（コードは変えない）。
   追記されたら 3.〜5. に戻り、また点検する。「Converged」（追記なし）になるか、3回に達したら次へ。
   **Converged は完了の判定ではない**。行政の自己点検にすぎず、合否は司法が出す。
7. **後の確認: 証拠表** — 基準ごとに、それを確かめる自動テストを特定して実行し、結果を記録する。
   テストの無い基準は隠さず「テストなし」と書く（司法はそれを RETRY にする）。
   ビルド・型・lint も実行する。実行できないものは「実行不能」と明記する（証拠なし扱い）。
8. **証拠を添えて指揮に返す** — 下の形式。**合否は書かない**。

## 手順（インライン契約）

1. 契約（合意された完了基準と検証方法）を確認する。曖昧・欠落があれば着手せず指揮に差し戻す。
2. 作業ブランチの上で実装する。差分は契約のスコープ内に保つ。実装本体は公式 `feature-dev` に委ねてよい。
3. 各基準に併記された検証方法を**1対1で実行する**。
4. 下の形式で指揮に返す。

## 返す形式

```
## 実装したこと
<契約のどの基準（FR-### / US<n>/AC<m> / インラインの基準）に対して、何を変えたか>

## 決定性の結果
| 基準 | 検証（テスト名・コマンド） | 結果 |
|---|---|---|
| FR-001 | `go test ./export -run TestCSVHeader` | 緑 / 赤 / 実行不能 / テストなし |

## 作り残しの点検（spec-kit 契約のとき）
<converge の回数と最終結果: Converged / 3回で未収束（残ったタスク）>

## 後の確認で元に戻した変更（spec-kit 契約のとき。あれば）
<例: .gitignore に /speckit-implement が追記した `.vscode/` の行を削除した>

## スコープ外に触れた点（あれば）
## 未解決・判断を要する点（あれば。仕様の誤り・不足はここ）
```

赤・実行不能・テストなしがあっても**隠さず出す**。握り潰した証拠で通った判定は、後で必ず高くつく。

## アンチパターン

- **合意前に実装を始める** — 承認済みの仕様、または Plan Mode の合意が無い状態で書き始めない。
- **自己レビューの結果を判定として扱う** — 「テストが通ったので完了です」「Converged なので完了です」と
  宣言しない。点検したこと自体は良い。結果は証拠として返す。
- **自己レビューを省く** — 差分を読み返さず、テストも回さずに返す。司法の差し戻しが増えるだけ。
- **正典を書き換える** — `spec.md` や constitution を実装 PR で変えない。仕様の変更は先に仕様の PR。
- **スコープを広げる** — 「ついでに直した」は契約外の変更で、レビューを困難にする。
- **赤を握り潰す** — 「おそらく無関係」で落とさない。無関係だと**決定性に**示せない限り赤は赤。
- **`/speckit-implement` を枠の外で呼ぶ** — 前後の確認が無いと、無人での停止・ignore ファイルへの範囲外の変更・証拠の欠落が素通りする。
