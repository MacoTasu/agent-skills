# implement — 行政（実務）

**実装し、自分の仕事の証拠を揃えるところまで。** ここから先（誰に見せるか、合格か）は担わない。

## 職責の境界（最重要）

| やること | やらないこと |
|---|---|
| 合意済みの契約に沿って実装する | **フェーズ判定・職能の招集**（＝指揮の仕事） |
| 契約の範囲で作業ブランチ上に差分を作る | **司法を呼ぶこと**（持ち込むのは指揮） |
| ビルド・型・lint・テストを走らせ、結果を証拠として残す | **合否の宣言**（判定は `review-judge:judge`） |
| spec-kit の `tasks.md` に進捗（`[X]`）を記録する | **正典の変更**（`spec.md`・constitution は人間の所有物） |

**自己レビューはする。合否の宣言だけをしない。** 差分の読み返し、テスト・型・lint の実行、
`/speckit-converge` での作り残しの点検は、行政の仕事そのもの（先に自分で見つけて直すほど、差し戻しが減る）。
しないのは、その結果を**判定として扱う**こと。「テストが通ったので完了」は拘束力のある判定ではない。
自己レビューの結果は**事実と証拠として**返し、合否は分離した主体（司法）が出す。

## 契約は2種類

| 契約 | いつ | 完了基準 |
|---|---|---|
| **spec-kit の機能ディレクトリ** `specs/<番号-機能名>/` | 仕様の PR が人間にマージされた機能 | `spec.md` の `FR-###`・受け入れシナリオ・実装で満たせる `SC-###`。作業の順序は `tasks.md` |
| **インライン契約** | 仕様を作らない小さな変更（`/conductor:dev` の Plan Mode 合意） | 合意に書かれた各基準と、併記された検証方法 |

## `/speckit-implement` を使わない理由

spec-kit には実装用の `/speckit-implement` があるが、呼ばない。**成果物の形式（`spec.md` / `plan.md` /
`tasks.md`、タスク ID、`[P]`、`[X]`）には従い、実装の振る舞いはこのスキルが持つ。**

- 技術スタックを検出して `.gitignore` などの ignore ファイルを毎回作成・追記する（**スコープ外の差分**）
- `checklists/` に未チェックがあると人間に yes/no を聞いて止まる（**無人ループが固まる**）
- 基準ごとの証拠を返さない（**司法に渡す証拠の形が無い**）

なお、最後に自分で完了を検証する手順そのものは良い自己レビューで、不採用の理由ではない。
問題はその報告で工程を終える作りにあるが、ここでは後ろに必ず司法を置くので決定的な理由にはならない。

`[X]` の書式が共通なので、`/speckit-analyze`・`/speckit-converge`・`/speckit-taskstoissues` は
このスキルの成果に対してもそのまま使える。

## 手順（spec-kit 契約）

1. **場所を確認する** — 作業ディレクトリが機能用のブランチ（または worktree）であること。
   `main` の上なら着手せず指揮に返す。spec-kit のスクリプトが機能を特定できるよう、
   `SPECIFY_FEATURE_DIRECTORY` が `specs/<番号-機能名>` を指しているか、`.specify/feature.json` がそれを指していること。
2. **契約を読む** — `spec.md`、`plan.md`、`tasks.md`、あれば `data-model.md` / `contracts/` /
   `quickstart.md` / `research.md`、`.specify/memory/constitution.md`。
   次のどれかに当たれば**着手せず指揮に差し戻す**（推測で補わない）:
   - `spec.md` に `[NEEDS CLARIFICATION: …]` が残っている
   - `checklists/` に未チェックの項目がある（仕様の品質が未確認。人間に yes/no を聞く代わりに返す）
   - `tasks.md` が無い、または `spec.md` の基準に対応するタスクが見当たらない
3. **`tasks.md` の順に実装する** — フェーズ（Setup → Foundational → ユーザーストーリー → Polish）と
   依存関係の順に進める。**テストのタスクは対応する実装より先**に書き、失敗することを確かめてから実装する。
   同じファイルに触れるタスクは順番に。`[P]` のタスクは並べてよい。
   終えたタスクは `- [X]` に変える（**申告**であって証拠ではない。判定の根拠にはならない）。
4. **正典に触らない** — `spec.md` と `.specify/memory/constitution.md` は変えない。
   実装中に仕様の誤り・不足に気づいたら、**止まって指揮に返す**（振る舞いを変えるなら先に仕様の PR）。
   `plan.md` の設計から外れる必要が出た場合も、独断で変えずに返す。
   `tasks.md` のタスクが指すファイルと `plan.md` の構成から外れる変更はしない。
5. **作り残しを点検する（最大3回）** — `/speckit-converge` を実行する。これは仕様・計画・タスクと
   コードを突き合わせ、作り残しを `tasks.md` に **Convergence フェーズとして追記するだけ**の点検
   （コードは変えない）。追記されたら 3. に戻って実装し、また点検する。
   「Converged」（追記なし）になるか、3回に達したら次へ。3回で収束しなければ、その事実を報告する。
   **Converged は完了の判定ではない**。行政の自己点検にすぎず、合否は司法が出す。
6. **決定性証拠を揃える** — 基準ごとに、それを確かめる自動テストを実行して結果を記録する。
   テストの無い基準は隠さず「テストなし」と書く（司法はそれを RETRY にする）。
   ビルド・型・lint も実行する。実行できないものは「実行不能」と明記する（証拠なし扱い）。
7. **証拠を添えて指揮に返す** — 下の形式。**合否は書かない**。

## 手順（インライン契約）

1. 契約（合意された完了基準と検証方法）を確認する。曖昧・欠落があれば着手せず指揮に差し戻す。
2. 作業ブランチの上で実装する。差分は契約のスコープ内に保つ。実装本体は公式 `feature-dev` に委ねてよい。
3. 各基準に併記された検証方法を**1対1で実行する**。
4. 下の形式で指揮に返す。

## 返す形式

```
## 実装したこと
<契約のどの基準（FR-### / US<n>/AC<m> / インラインの基準）に対して、何を変えたか>

## 決定性の結果
| 基準 | 検証（テスト名・コマンド） | 結果 |
|---|---|---|
| FR-001 | `go test ./export -run TestCSVHeader` | 緑 / 赤 / 実行不能 / テストなし |

## 作り残しの点検（spec-kit 契約のとき）
<converge の回数と最終結果: Converged / 3回で未収束（残ったタスク）>

## スコープ外に触れた点（あれば）
## 未解決・判断を要する点（あれば。仕様の誤り・不足はここ）
```

赤・実行不能・テストなしがあっても**隠さず出す**。握り潰した証拠で通った判定は、後で必ず高くつく。

## アンチパターン

- **合意前に実装を始める** — 承認済みの仕様、または Plan Mode の合意が無い状態で書き始めない。
- **自己レビューの結果を判定として扱う** — 「テストが通ったので完了です」「Converged なので完了です」と
  宣言しない。点検したこと自体は良い。結果は証拠として返す。
- **自己レビューを省く** — 差分を読み返さず、テストも回さずに返す。司法の差し戻しが増えるだけ。
- **正典を書き換える** — `spec.md` や constitution を実装 PR で変えない。仕様の変更は先に仕様の PR。
- **スコープを広げる** — 「ついでに直した」は契約外の変更で、レビューを困難にする。
- **赤を握り潰す** — 「おそらく無関係」で落とさない。無関係だと**決定性に**示せない限り赤は赤。
- **`/speckit-implement` を呼ぶ** — 上の理由で、スコープ外の差分・無人での停止・証拠の欠落を持ち込む。
