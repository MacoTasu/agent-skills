# 実装のあとの確認（後の確認）

> `dev-crew:implement` が、書き終えてから指揮に返すまでに行う確認の一覧。`SKILL.md` の手順から Read する。
> **`SKILL.md` が指した節（「spec-kit 契約」か「インライン契約」のどちらか）だけを、上から順に全部行う。もう一方の節は行わない。**
> **そのあと「報告の前（どちらの契約でも）」を全部行う。**
> 末尾に課題番号（`#数字`）の無い項目は、`SKILL.md` の手順にあった記述をそのまま移したもの。
> 「差分の見方」の節と、課題番号のある項目は、あとからこのファイルに足したもの（このファイルが正。
> 項目の末尾の括弧書きは、`reference/failure-criteria.md` の基準と出典の課題）。
>
> **手当ての置き場。** 振り返り（retro）の記録で、失敗の基準に当てはまることが繰り返し起きたとき、実装のあとの確認への手当ては、この一覧の項目として足す。
> 足す・変えるのは、人間がこのファイルへの変更をマージしたときだけ。
> どの種類の手当てがどこに着地するかの索引は、本プラグイン同梱 `reference/failure-criteria.md`「着地の索引」。

## 差分の見方

この一覧で「変更したファイルの一覧」と言うときは、次の 2 つを合わせたもの。確認のたびに、その場で求める。

- `<基点>` は、`git fetch origin` のあとの `git merge-base origin/main HEAD`（PR の向き先が `main` でなければ、その枝。指揮・司法も同じ 1 行で取る）。求められなければ、先へ進まず「基点を解決できない」と報告する。
- `git diff --name-status <基点>`（コミット済みと未コミットの変更。`D` は削除）と、`git ls-files -o --exclude-standard`（未追跡の新規ファイル）。
  `<基点>...HEAD` の形は、未コミットの変更を返さないので使わない。

## spec-kit 契約

番号は `SKILL.md`「手順（spec-kit 契約）」の続き（4.〜8.）。

4. **範囲外の変更** — 作業前の状態と比べて、変わったファイルを一覧にする。
   - `spec.md` と `.specify/memory/constitution.md` が変わっていたら元に戻し、指揮に報告する（正典は変えない）。
     指揮が「仕様の変更を認める経路」と明示しているときの、契約の機能ディレクトリの `spec.md` と `plan.md` だけは元に戻さず（ほかの機能の `spec.md` と constitution は戻す）、
     `git diff <基点> -- specs/<機能>/spec.md specs/<機能>/plan.md` の全件（この実行で変えた分だけでなく、基点との差分の全部）を 1 件ずつ `SKILL.md`「返す形式」の「仕様の変更」に書く。
   - **ignore ファイル**（`.gitignore` / `.dockerignore` / `.npmignore` / `.eslintignore` / `.prettierignore` など）が、
     `tasks.md` のタスクに無いのに変わっていたら、**この実行で加わった変更だけを元に戻し**（この実行で新規作成されたものは削除し）、
     何を戻したかを報告する。元から存在した内容には触れない。
   - それ以外で `tasks.md` のタスクが指すファイル・`plan.md` の構成から外れる変更があれば、「スコープ外に触れた点」として報告する。
   - **計画・タスクとの食い違い** — 変更したファイルの一覧（上の「差分の見方」）を、次の 3 つと突き合わせる。
     当たったら `plan.md` は自分で直さず（仕様の変更を認める経路で、`spec.md` の変更に伴う修正は除く。直したら「仕様の変更」に申告する）、報告の「スコープ外に触れた点」に「どの記述と食い違うか・優先した指示・理由」を書く。（`plan-conflict` #47 #87）
     - `grep -nE '変えない|触らない|変更しない' specs/<機能>/plan.md` の行が指すパスが、一覧に在る。`plan.md` が基点と違うときは、
       基点の版（`git show <基点>:specs/<機能>/plan.md | grep -nE '変えない|触らない|変更しない'`）にも当て、そこで当たったものは「仕様の変更」にも申告する。
     - `tasks.md` に「削除」「消す」と書かれたパスが残っている（`test -e <パス>` が成功する）。
     - `grep -n '^- \[ \]' specs/<機能>/tasks.md` に出たタスクが指すパスが、一覧に在る（実装したのに `[X]` が無い）。
5. **自己レビュー** — 差分を読み返し、テスト・型・lint を実行する。直せるものは直す（自分の仕事の範囲で）。
6. **作り残しの点検（最大3回）** — `/speckit-converge` を実行する。仕様・計画・タスクとコードを突き合わせ、
   作り残しを `tasks.md` に **Convergence フェーズとして追記するだけ**の点検（コードは変えない）。
   追記されたら `SKILL.md` の手順 3.（書く）に戻って 4.・5. をやり直し、また点検する。「Converged」（追記なし）になるか、3回に達したら次へ。
   **Converged は完了の判定ではない**。行政の自己点検にすぎず、合否は司法が出す。
7. **見た目の証拠（UI に触れたとき）** — 同じディレクトリの `record-visual-evidence.md` を Read して従う。
   対象リポジトリの `.claude/visual-evidence.json` の `ui_paths` と差分の交わりで該当を決め、該当すれば録画シナリオを用意・更新して
   **after（自分の worktree）と before（merge-base の一時 worktree）を自分で録画**する。該当しなければ「該当なし」、
   撮れなければ「未録画（理由）」。結果は `SKILL.md`「返す形式」の `🎬 見た目の証拠（案）` に書く。添付と PR 作成は指揮の仕事。
8. **証拠表** — 基準ごとに、それを確かめる自動テストを特定して実行し、結果を記録する。
   テストの無い基準は隠さず「テストなし」と書く（司法はそれを RETRY にする）。
   ビルド・型・lint も実行する。実行できないものは「実行不能」と明記する（証拠なし扱い）。
   - 証拠表には、`spec.md` の FR・受け入れシナリオに加えて、Edge Cases 節の項目も 1 行ずつ載せる
     （`awk 'tolower($0) ~ /^#+ *edge cases/{f=1;next} /^#+ /{f=0} f && /^[-*] /' specs/<機能>/spec.md` に出た行の数だけ。
     `grep -ciE '^#+ *edge cases' specs/<機能>/spec.md` が 0 なら、項目 0 件とせず「Edge Cases の見出しが見つからない」と報告に書く）。
     報告の前に表の「テストなし」の行を数え、0 でなければテストを足す。足せない行は「未解決・判断を要する点」に挙げ、完了と書かない。（`untracked-removal` #57）
   - 契約に検証コマンドが書かれた基準は、下の「インライン契約」の 3. の補足のとおりに扱う。

## インライン契約

番号は `SKILL.md`「手順（インライン契約）」の続き（3.〜4.）。

3. 各基準に併記された検証方法を**1対1で実行する**。
   - 契約のコマンドは**文面どおり**実行し、結果を（赤・実行不能でも）そのまま返す。通らないときは、実装を契約に合わせる。
     合わせられない（コマンドが成り立たない）ときは、契約の表を書き換えず、報告の「未解決・判断を要する点」に
     「契約: <原文> → 結果、成り立たない理由」を書く。代わりのコマンドを実行したなら「実際: <実行したもの>」も同じ行に書き、
     その基準を緑にしない。（`verification-swapped` #27 #90）
4. UI に触れたら見た目の証拠を撮る（上の「spec-kit 契約」の 7. と同じ。`record-visual-evidence.md`）。

## 報告の前（どちらの契約でも）

上の節を終えたあと、指揮に返す報告を書く前に全部行う。差し戻しの修正で差分が動いたら、やり直す。

- **報告の主張が実体と合うか** — 報告（PR 本文の案を書いたなら、それも）に書いたパスを、変更したファイルの一覧（「差分の見方」）と 1 つずつ突き合わせる。
  「変えた・作った」と書いたパスは、一覧に在り `test -e <パス>` が成功すること。「削除した」と書いたパスは、一覧に `D` で在り `test -e <パス>` が失敗すること。
  合わない記述は本文から消す。リポジトリの外のパス（一時ディレクトリの動画など）は `test -e` だけで見て、確かめられなければ「未確認」と書く。（`claim-mismatch` #86 #93）
- **コマンド例を実行したか** — `git diff <基点>` と未追跡の新規ファイルを読み、足した・変えたシェルのコマンド例
  （コードブロック、文中のバッククォート、スクリプト）を拾って、一時ディレクトリで実際に実行する。
  入力は 2 通り: 代表的な値（`#`・`/`・空白を含む URL など）と、途中のコマンドが失敗する場合（削除などの危険な側へ進まないこと）。
  実行しなかった例は、報告の「未解決・判断を要する点」に「未実行（理由）」と書く。（`unreliable-check` #40）
- **「CI で走る」と書くテストが、CI の実行対象に入るか** — 足した・変えたテストを報告に「CI で走る」と書く前に、CI の設定
  （`.github/workflows/` と、そこから呼ばれるテストの設定の実行対象）がそのファイルのパスを含むことを確かめ、含むと言える設定の行を報告に引く。
  含まないもの（録画用のシナリオなど）は「CI の対象外」と書き、基準を守るテストに数えない。（`evidence-conditions` #67）
- **作った実行物を手で動かすなら、その前に** — `env | cut -d= -f1 | grep -iE '(_ENV|_SOCKET|_PANE_ID|_SESSION)$'` に出た変数
  （実環境を指しうる）を `env -u <変数> <コマンド>` で外すか、`HOME` と状態の置き場を `mktemp -d` のディレクトリに向けて実行する。
  外さずに実行したら、報告の「スコープ外に触れた点」に、書き込まれた場所を書く。（`unguarded-broad-op` #49）
