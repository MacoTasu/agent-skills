# 失敗の基準の一覧

振り返り（retro）で「何が起きたら、どの失敗として数えるか」を先に決めておくための一覧。
1 つの基準は、名前・当てはまるとき・当てはまらない例・手当ての置き場・出典で書く（ほかの基準と重なるものには「重なる例」も書く）。

- **基準を足す・変えるのは、人間がこのファイルへの変更をマージしたときだけ。**
- **`dev-crew:retro`（`agents/retro.md`）は、招集のたびにこのファイルを Read し、PR で起きた出来事を基準に当てはめて記録する。**
  記録の形は `retro-record.md`。記録だけで、課題は作らない。回数を見て変更を起こす役は、まだ無い（後の段階）。
- 初版は、それまでに立った retro の課題 57 件を、同じ手当てで片付くまとまりに束ねて起こした。出典はこのリポジトリの課題番号。
  まとまりは 14 個だった。そのうち「報告・PR の説明・変更が、合意した内容と突き合わされない」の 1 つを、突き合わせる相手ごとに 3 つ
  （`verification-swapped` / `claim-mismatch` / `plan-conflict`）に割ったので、基準は 16 個（と `other`）。
  あとから足した基準は、出典に PR の番号を書いてある（`unread-rule`）。
- 記録に書くのは「何が起きたか」（この一覧の基準）と「何が止めたか」（事実）。「どこで止めるべきだったか」は記録に書かない。
  手当ての置き場は、回数を見て変更を起こすときに、下の「着地の索引」と各基準の「手当ての置き場」から決める。

## この一覧のために新しく置いた決まり

次の 3 つは、既存の決まりを写したものではなく、この一覧のために新しく置いた。

1. **1 つの出来事が複数の基準に当てはまるときは、当てはまる基準をすべて付ける。回数は基準ごとに数える。**
   各基準の「当てはまらない例」は、その基準**だけ**では拾わないものの例。「→ 別の基準」と書いたものは、そちらの基準で拾う
   （両方の「当てはまるとき」を満たす出来事には、両方を付ける）。
2. `other` が似た形で繰り返すなら、新しい基準の候補として人間が読む。
3. 「人が決めること」に当たる手当ては、ファイルへの変更にしない。決めてほしいこととして人間に出す。

## 着地の索引

基準に当てはまることが繰り返し起きたとき、手当てをどこへの変更として書くか。

| 手当ての種類 | 着地する場所 | いま在るか |
|---|---|---|
| 契約に必ず書く基準・検証方法 | `conductor` 同梱 `reference/inline-contract.md` | 在る |
| 実装のあとの確認 | `dev-crew` 同梱 `skills/implement/reference/post-checks.md` | 在る |
| 書記に渡すもの・観点 | `conductor` 同梱 `reference/scribe-checklist.md` | 在る |
| 機械的な検査（リポジトリの lint。commit のときに止める） | ハーネスのリポジトリ直下の `.githooks/lint.sh`（`.githooks/pre-commit` が呼ぶ。規則の足し方はそのファイルの先頭。プラグインには同梱しない） | 在る |
| 機械的な検査（作業中の操作を止める hook） | `dev-crew` 同梱 `hooks/guard-broad-op.sh`（配線は `hooks/hooks.json`。規則の足し方はスクリプトの先頭） | 在る |
| 手順書の本文（指揮・親子・retro の手順など、上のどれにも入らない手順） | その手順書（最後の手段。上のどれにも置けないときだけ） | 在る |
| 人が決めること | ファイルへの変更にしない（上の「この一覧のために新しく置いた決まり」の 3.） | — |

- 置き場は、人の注意に頼らない順に試す: 機械的な検査 → 確認の一覧（実装のあとの確認・書記の観点）→ 契約のテンプレート → 手順書の本文。
  機械的に止められるものは、機械的な検査に置く。
- インライン契約のテンプレートが受けるのはインライン契約だけ。spec-kit 契約の側（対象リポジトリの仕様・タスクのテンプレート）はハーネスの外にある。

## 基準

### `verification-swapped` — 検証方法の黙った差し替え

- **当てはまるとき**: 契約に書かれた検証方法と、実際に実行したものが違うのに、その違いが完了報告にも PR 本文にも書かれていなかった。
  成果物の置き場所や形を変えた結果、契約の文面どおりのコマンドが通らなくなった場合を含む。
- **当てはまらない例**: 検証方法が成り立たないことを報告し、合意し直してから進めた。契約のコマンドが合意の時点で動かなかったこと自体（→ `unreliable-check`）。
- **重なる例**: 契約のコマンドを実行したと報告しつつ、別のコマンドを実行した（`claim-mismatch` も付ける）。
- **手当ての置き場**: 実装のあとの確認。
- **出典**: #27 #90

### `claim-mismatch` — 報告・PR 本文の主張と実体の不一致

- **当てはまるとき**: 完了報告や PR 本文に書いたこと（変更した箇所、用意したファイルのパス、要注意の変更の申告）が、いまの差分・作業ツリーの実体と合っていなかった。
  途中で戻した変更が本文に残った場合、該当する変更があるのに申告の節に書かれていない場合を含む。
- **当てはまらない例**: 契約の検証方法と実行したものの違い（→ `verification-swapped`）。本文は実体どおりで、実装そのものが契約を満たしていない（失敗の基準の対象外。司法の判定で扱う）。
- **重なる例**: 契約のコマンドを実行したと報告しつつ、別のコマンドを実行した（`verification-swapped` も付ける）。
- **手当ての置き場**: 実装のあとの確認（#86 #93）。指揮が人間へ中継する前の確認は手順書の本文（#93）。
  PR 本文の申告の不足（#55）は hook にしていない（該当の判定が言語ごとに違い、誤検出なく書けない）。
  PR 本文案の申告は、司法の前に書記 1 人が差分と突き合わせる（書記に渡すもの・観点。手順は `conductor` 同梱 `reference/parent-child.md`「実装から PR まで」の 3.。PR #101 PR #103 PR #104 PR #105 PR #106 PR #107）。
  そのあと、司法が PR を作る前に本文案の検査で差し戻している（`review-judge` 同梱 `agents/judge.md`。1 ラウンドは使う）。
- **出典**: #55 #86 #93 PR #101 PR #103 PR #104 PR #105 PR #106 PR #107（PR の番号は、課題ではなく、PR に残した振り返りの記録）

### `plan-conflict` — 計画・タスクと変更の食い違い

- **当てはまるとき**: 変更したファイル・残したファイルが、派生の文書（計画の「変えない」、タスクの「削除する」など）と食い違ったまま、理由の記録も文書の更新も無く進んだ。
  指揮が実装担当に渡した制約（「このファイルには差分を出さない」など）が、承認済みの計画・タスクと食い違っていた場合を含む。
- **当てはまらない例**: 食い違いに気づき、どちらを優先したかと理由を報告か PR 本文に書いた。仕様そのものを満たしていない（失敗の基準の対象外。司法の判定で扱う）。
- **手当ての置き場**: 実装のあとの確認（#47 #87）。制約を渡す前の確認は手順書の本文（#88。#47 のコメントにある「仕様のディレクトリを変えない制約から、`tasks.md` の `[X]` を除く」も同じ場所）。
- **出典**: #47 #87 #88

### `unreliable-check` — 当てにならない確かめ方

- **当てはまるとき**: 契約や指示文に書いた確かめ方そのものが、確かめになっていなかった。
  (1) 書かれたコマンドが実行できない、(2) コマンド例が代表的な入力で失敗する、(3) 足した判定が直す前の状態でも通る、(4) 前提が壊れていても通る（空振り）。
- **当てはまらない例**: 確かめ方は正しく動き、実装の誤りを赤にした。その種類の要件に要る確かめ方が、契約に書かれていなかった（→ `missing-check-form`）。
- **手当ての置き場**: インライン契約のテンプレート（#23 #48 #91）。実装のあとの確認（#40）。
- **出典**: #23 #40 #48 #91

### `missing-check-form` — 要件の種類に合った確かめ方の欠落

- **当てはまるとき**: 要件の種類ごとに決まって要る確かめ方が、契約に無かった。これまでに出た種類:
  値が 0／空になること、何かを外す・消すこと、文字列の解析・抽出（境界の入力）、定期的に走る処理（2 回続けて・同時に）、
  意味が重なるパラメータの同時指定、外部プロセスの起動（認証の確認・生死の確認・終了コードの順序）。
- **当てはまらない例**: 確かめ方は契約にあったが、空振りした（→ `unreliable-check`）。種類として繰り返さない、その変更だけの見落とし（→ `other`）。
- **重なる例**: 認証の入口ごとの確かめ方が契約に無かった（`unsourced-safety-claim` も付ける）。
- **手当ての置き場**: インライン契約のテンプレート。
- **出典**: #37 #56 #58 #59 #60 #83

### `evidence-conditions` — 証拠の取り方が決まっていない

- **当てはまるとき**: 証拠をどの条件で取るかが合意に無く、取った証拠が使えなかった、または取れなかった。
  例: CI でしか走らない検証が、PR を作るまで走らない。申告したテストが CI の実行対象に入っていない。
  PR を分けたとき、録画のシナリオがその PR のツリーに無い。証拠の書式に、起きた状態を書く行が無い。
- **当てはまらない例**: 証拠は決めた条件で取れていて、中身が赤だった。確かめ方そのものの空振り（→ `unreliable-check`）。
- **手当ての置き場**: インライン契約のテンプレート（#61）。#64 は spec-kit 契約でだけ起きるので、インライン契約のテンプレートには届かない（spec-kit 契約の側はハーネスの外）。実装のあとの確認（#67）。証拠の書式を定める手順書の本文（#85）。
  PR を作る順序は手順書の本文（#78。`conductor` 同梱 `reference/parent-child.md`「実装から PR まで」。条件の行を書かせる文は、spec-kit 契約の側には届かない）。
- **出典**: #61 #64 #67 #78 #85

### `mechanical-slip` — 指示文・スクリプトの機械的な誤り

- **当てはまるとき**: 指示文（markdown）やスクリプトに、決まった形の検査で見つかる誤りがあり、人や書記の目で初めて見つかった。
  例: 節の名前で指した先に見出しが無い。引用ブロックの直後に空行が無い。コードブロックの中で、シェルに渡らない変数を使う。
  真偽値に既定値の演算子を付けて意味が反転する。必須の見出しが欠けている。
- **当てはまらない例**: 文の意味や手順の組み立ての誤り（形の検査では見つからない。→ `instruction-consistency` か `other`）。
- **重なる例**: 読む側が前提にする見出しが欠けた（`instruction-consistency` も付ける）。
- **手当ての置き場**: 機械的な検査（リポジトリの lint）。送り出す前に確かめるものは手順書の本文（#76）。
- **出典**: #25 #26 #31 #76 #81

### `unsourced-safety-claim` — 出典・検証の無い安全の主張や決定

- **当てはまるとき**: 「断る」「通さない」「限定する」という安全・権限の主張や、「人が決めた」という記録が、入口ごとの検証や人の発言の引用を伴わずに、
  契約・説明書・依頼文に書かれた。例: 認証の入口の一部しか確かめていない。通す操作の副作用による迂回が挙がっていない。
  マシン全体の状態を変える操作が合意に無い。曖昧な発言を決定として記録した。書記への依頼文に「決定済み」と書いた。
- **当てはまらない例**: 主張に入口ごとの検証の結果が付いている。人の明示の回答を引用して記録している。外部の事実（版の安全性など）の出典が無い（→ `contract-blind-spot`）。
- **重なる例**: 認証の入口ごとの確かめ方が契約に無かった（`missing-check-form` も付ける）。
- **手当ての置き場**: インライン契約のテンプレート（#82 #89 #92 #94。#89 #94 は、合意の対象にする操作・回答の引用を完了基準に書かせる行）。書記に渡すもの（#95）。
- **出典**: #82 #89 #92 #94 #95

### `stale-mentions` — 既存の記述の洗い出し漏れ

- **当てはまるとき**: 語・要件・出力を置き換える／廃止する／足す変更で、古い前提のままの記述やテストが残った。
  洗い出しの対象（仕様や文書のディレクトリ、まだマージされていない PR、依頼に列挙した箇所）が足りない・裏取りされていない場合を含む。
- **当てはまらない例**: 洗い出したうえで、残す理由を書いて残した。消したものの行き先が無い（→ `untracked-removal`）。
- **手当ての置き場**: インライン契約のテンプレート（#32）。#68 は spec-kit 契約でだけ起きるので、インライン契約のテンプレートには届かない（spec-kit 契約の側はハーネスの外）。依頼ファイルの書き方は手順書の本文（#50 #77）。
- **出典**: #32 #50 #68 #77

### `contract-blind-spot` — 前提・影響範囲・戻し方の無い合意

- **当てはまるとき**: 合意の内容に、(1) 前提にした外部の事実の一次情報、(2) 変更が効く実行環境ごとの対象／対象外、(3) 壊す変更の戻し方、
  のどれかが無く、人の質問やレビューで初めて補った。
- **当てはまらない例**: 安全・権限の主張に検証が無い（→ `unsourced-safety-claim`）。削除する手順そのものの安全条件（→ `unsafe-deletion`）。
- **手当ての置き場**: インライン契約のテンプレート（#70 #71）。#62 は spec-kit 契約でだけ起きるので、インライン契約のテンプレートには届かない。
  仕様を起草する手順書の本文で、壊す変更があるときに、戻し方がそのとおり実行できるかを、人間に提示する前に確かめる（`spec-intake` 同梱 `skills/spec-draft/SKILL.md` の手順 6、`conductor` 同梱 `reference/parent-child.md`「種別: 仕様の起草」の 2.）。
- **出典**: #62 #70 #71

### `unguarded-broad-op` — 止まらない広範囲・不可逆の操作

- **当てはまるとき**: 作業中に、範囲の広い操作や取り返しのつきにくい操作が、機械的に止められずに実行された。
  例: 名前のパターンでのプロセス停止。範囲を絞らない書き込みの整形。基点を巻き戻すリセット。未追跡のファイルを巻き込む一括のステージ。
  実環境を指す変数を残したままの手動実行。
- **当てはまらない例**: 手順書に書く削除の手順の穴（→ `unsafe-deletion`）。全体の状態を変える操作が合意に無かったこと（→ `unsourced-safety-claim`）。
- **手当ての置き場**: 機械的な検査（作業中の操作を止める hook。#46 #52 #66 #75）。実装のあとの確認（#49）。
- **出典**: #46 #49 #52 #66 #75

### `untracked-removal` — 行き先の無い削除・載せ漏れ

- **当てはまるとき**: 削った記述・テストや、対応表に載せなかった項目について、「どこへ移したか／なぜ載せないか」の対応が無く、
  守られていた振る舞いや記述が消えた、または確かめられないまま残った。
  例: 置き換えたテストが守っていた別の振る舞い。文書を参照に置き換えたときに消した記述。対応表に載らなかった仕様の項目。
- **当てはまらない例**: 消したものごとに、移し先か消す理由が書かれている。置き換えで古い記述が残った（→ `stale-mentions`）。
- **手当ての置き場**: 実装のあとの確認（#57）。インライン契約のテンプレート（#63）。書記の観点（#69）。
- **出典**: #57 #63 #69

### `stale-base` — 古い基点のまま進む

- **当てはまるとき**: 基点のブランチが先に進んだのに、古い基点のまま検証・レビュー・PR 作成に進んだ。
  例: 司法の招集のときに基点と衝突して証拠が取れない。書記に渡した差分に、すでに基点に入った他の変更が混ざる。
- **当てはまらない例**: 基点に追従したうえで、並行して入った変更が仕様の前提を崩した（→ `other`）。
- **手当ての置き場**: 子の手順は手順書の本文（#51）。書記に渡すもの（#53）。
- **出典**: #51 #53

### `retro-reliability` — 振り返り自体の確実さと運用

- **当てはまるとき**: 振り返りの記録や運用そのものが確かでなかった。
  例: 招集は成功の扱いなのに、コメントが投稿されていない。置き換え用の印が残ったまま投稿されうる。同じ原因の課題が重なり、読む手間が提案の価値を上回る。
- **当てはまらない例**: 振り返りが見つけた、開発の側の失敗（それぞれの基準で数える）。
- **手当ての置き場**: 手順書の本文（#38 #41。`agents/retro.md`「投稿の形」の、投稿の前の検査と読み戻し）。
  機械的な検査（作業中の操作を止める hook。#41 の、置き換え用の印が残ったままの投稿）。
  #65（いつ課題にするか）も手順書の本文: PR ごとの振り返りは課題を作らず、記録だけを残す（`retro-record.md`）。
  1 回の被害が大きい出来事は、課題にせず `severe` の印を付けて人間に伝える（同ファイル）。
- **出典**: #38 #41 #65

### `unsafe-deletion` — 削除を伴う手順の安全条件と倒れ方

- **当てはまるとき**: 削除・上書きを伴う手順で、(1) 安全条件が見ているものと、削除が実際に消すものが食い違っていた、
  (2) 判定に使うコマンドが失敗・空の出力のときに「消す」側へ進んだ、(3) 検出から削除までの間に確かめ直しが無かった。
- **当てはまらない例**: 作業中の単発の操作（→ `unguarded-broad-op`）。壊す変更の戻し方が合意に無い（→ `contract-blind-spot`）。
- **手当ての置き場**: インライン契約のテンプレート。
- **出典**: #44 #45

### `instruction-consistency` — 指示文を書く変更の整合

- **当てはまるとき**: エージェントへの指示文を書く・変える変更で、(1) 見出しやブロック名など機械で読む約束事を、読む側だけが前提にし、書く側の定義が無かった、
  (2) 入力が欠けたときの扱いが決まっていない、または同じ入力に 2 つの扱いが併存した。
- **当てはまらない例**: 決まった形の検査で見つかる誤り（→ `mechanical-slip`）。
- **重なる例**: 読む側が前提にする見出しが欠けた（`mechanical-slip` も付ける）。
- **手当ての置き場**: インライン契約のテンプレート。
- **出典**: #21 #22

### `unread-rule` — 足した決まりが読まれない

- **当てはまるとき**: 手順書や一覧に決まりを足した（または決まりを置くファイルを新しく作った）が、その決まりを実行する役が
  そのファイルを読む決まり（手順の中の「Read する」など）が無く、足した決まりが効かないまま進んだ。
  参照の 1 文や案内があるだけで、いつ・どの役が読むかが決まっていない場合を含む。
- **当てはまらない例**: 読む決まりがあり、読んだうえで守らなかった（起きたことに合う基準で数える）。
  見出しやブロック名など機械で読む約束事を、読む側だけが前提にした（→ `instruction-consistency`）。置き換えで古い記述が残った（→ `stale-mentions`）。
- **手当ての置き場**: インライン契約のテンプレート（決まりを足す変更の完了基準に、「どの役が、どの手順で、そのファイルを読むか」を書く）。
- **出典**: PR #96 PR #97（課題ではなく、PR に残した振り返りの記録。どちらも `other` として記録された）

### `other` — その他（どれにも当てはまらない）

- **当てはまるとき**: 上のどの基準の「当てはまるとき」も満たさない。
- **当てはまらない例**: 上の基準のどれかを満たしている（その基準で数える）。
- **手当ての置き場**: 無い（冒頭の「この一覧のために新しく置いた決まり」の 2.）。
- **出典**: なし
