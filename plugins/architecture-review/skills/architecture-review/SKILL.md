# アーキテクチャ整合性レビュー

## このスキルの守備範囲

見るのは「**壊れないか**」——DB と外部世界の状態が食い違わないか。

隣接するスキルとの境界:

- 公式 `pr-review-toolkit`（コードの書き方）とは重ならない。特に
  `silent-failure-hunter` が「エラーを握り潰していないか」を見るのに対し、
  こちらは「**再実行されても壊れないか**」を見る。視点が違うので両方必要。
- `saas-review`（マルチテナント・課金・監査ログなど、SaaS という事業形態に固有の性質）とも
  重ならない。SaaS のバックエンドを変更する PR では、両方を読む価値がある。
- 「壊れたことを知れるか・止められるか」（可観測性・kill switch）は `saas-review` の
  観測性の軸にある。

## 使い方

1. レビュー対象の差分を取る（`git diff`、`gh pr diff <N>` など）。
2. 差分に外部 API 呼び出し・非同期ジョブ・キューが含まれるか確認する。無ければ
   このスキルは不要。
3. `checklists/*.md` の各項目の **「どう検出するか」を実際に実行する**。読んで想像せず、
   grep する・ファイルを開く・コマンドを走らせる。
4. 検出できた事実だけを指摘する。確認できなかった項目は「未確認」と明示する。

## 軸

| 軸 | ファイル | 差分にこれがあれば読む | status |
|---|---|---|---|
| 外部連携とトランザクション整合 | `checklists/external-integration-consistency.md` | メール送信 / 決済 / 通知 / 送信する webhook / 非同期ジョブ / キュー | draft |

`status` は `draft`（書いたが実PRでの検証を経ていない）/ `verified`（実際の PR で使い、
指摘として成立した実績がある）。

## 項目の書式

- **観点**: 何を見るか
- **なぜ危険か**: 守らなかった時に実際に起きる事故
- **どう検出するか**: 見るファイル・grep・実行コマンド（**エージェントが実行できる形で書く**）
- **よくある間違った実装**: 実際に踏まれるパターン

「どう検出するか」が書けない項目は、レビューで実行できない＝ポエムなので採用しない。
