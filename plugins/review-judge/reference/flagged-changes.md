# 要注意の変更（PR 本文で申告する）

> 司法(`review-judge:judge`)と指揮が参照する、実装 PR の本文に必ず置く **「⚠️ 要注意の変更」節**の決まり。
> 何が要注意に当たるか・申告の書式・司法がどう検査するかを定める。
> 直後に置く「🎬 見た目の証拠」節は `visual-evidence.md`。

## 何が要注意に当たるか

次に触れる変更も**PR 作成までは進めてよい**。マージは常に人間が行うので、止める位置はマージ前で足りる。
代わりに、人間がマージ判断で見落とさないよう **PR 本文の先頭で申告する**:

- security（認証/認可/秘匿情報/入力検証）
- 課金・決済・コスト発生
- 本番データの破壊的変更・不可逆マイグレーション
- 公開 API の後方互換を壊す変更

## 申告の書式

PR 本文の先頭に置く。該当が無くても「なし」と書く＝「確認して該当なし」と「確認し忘れ」を区別する。

```
## ⚠️ 要注意の変更
- [認証/認可] path/to/file: 何が変わるか・なぜ要注意か
レビューで特に見てほしい点: …
```

```
## ⚠️ 要注意の変更
なし
```

実装 PR が契約の `spec.md`・`plan.md` を変えたときの `[仕様の変更]`・`[仕様の変更・要件を弱めた]`・`[計画の変更]` の行も
この節に書く。その行の書式と突き合わせ方の正は `contract-speckit.md`「正典の不可侵と仕様の変更」。

## 司法の検査

司法は**申告が差分と一致しているか**を判定する。差分が上の対象に触れているのに
申告が無い・不正確なら **RETRY**（申告漏れのまま PR を出させない）。
要注意の変更であること自体は ESCALATE の理由にしない（マージは人間が行い、そこで申告を読む）。
