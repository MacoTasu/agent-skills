# 契約の読み方: spec-kit の機能ディレクトリ

契約 (a) として **`specs/<番号-機能名>/`**（[spec-kit](https://github.com/github/spec-kit) が作る
機能ディレクトリ）を渡されたときの読み方。`goals/<slug>.md` を渡されたときは `judge.md` 本文のとおり。

**判別**: 渡されたパスが `spec.md` を含むディレクトリなら spec-kit の契約。

## 前提: 仕様は先にマージされている

spec-kit の契約は **Living Spec** として扱う。`spec.md` が契約で、`plan.md` と `tasks.md` はそこから
導かれた派生物。振る舞いを変えるときは、**実装より前に** `spec.md` を直す PR を人間がマージする
（＝立法の承認）。したがって実装 PR が来た時点で、`main` の `spec.md` は新しい振る舞いを
すでに記述している。

## 何を読むか

| ファイル | 正典か | 何として使うか |
|---|---|---|
| `spec.md` | **正典** | 完了基準。`FR-###`、ユーザーストーリーの受け入れシナリオ（`US<n>/AC<m>`）、実装で満たせる `SC-###`、Edge Cases |
| `.specify/memory/constitution.md` | **正典** | ガードレール。MUST の原則への違反は契約違反 |
| `plan.md` | 派生 | 技術的な制約・構成。スコープの境界（触ってよい場所）の目安 |
| `tasks.md` | 派生 | 行政の作業記録。`[X]` は**申告**であって証拠ではない |
| `quickstart.md` / `contracts/` | 派生 | 検証手順とインタフェース。決定性チェックの材料 |

`spec.md` がテンプレートのままの項目や、`[NEEDS CLARIFICATION: …]` が残っている場合は、
**契約自体の不備**として `ESCALATE`（実装側では解消できない）。

## 基準 ↔ 決定性証拠の対応づけ

`goals/` の契約は各基準に検証コマンドを併記するが、spec-kit の `spec.md` は技術に依存しない書き方を
するので、検証方法は書かれていない。代わりに**自動テスト**を検証方法として対応づける。

1. `spec.md` から基準の一覧を作る: 各 `FR-###`、各受け入れシナリオ、実装で満たせる `SC-###`。
   公開後にしか測れない指標（利用率・満足度・事業 KPI）は**対象外**と明記して除く。
2. 各基準について、それを確かめる**自動テスト**を特定する。手がかりは次の順:
   - テストコード中の基準 ID（`FR-001`、`US1` など）の言及 — `git grep -n 'FR-001'`
   - `tasks.md` のテスト作成タスクが指すファイル
   - `quickstart.md` の検証シナリオ、`contracts/` に対応する契約テスト
3. 特定したテストを**自分で実行する**。行政の「緑でした」や `tasks.md` の `[X]` は根拠にしない。
4. 判定:
   - **テストが特定できない基準が1つでもある** → `RETRY`（証拠不足）。どの基準にテストが無いかを列挙する。
     spec-kit ではテストが任意なので、ここが最も起きやすい不足。
   - テストが赤 → `REJECT`。
   - `tasks.md` に未完了（`[ ]`）のタスクが残っている → `RETRY`（未完）。
     逆に全部 `[X]` でも、それだけでは PASS の根拠にならない。

出力の「⚙️ 決定性チェック」には、**基準 ID ↔ テスト ↔ 結果**の対応表を載せる。

## 正典は実装 PR で変えてはいけない

- **`spec.md` と `.specify/memory/constitution.md` は人間の所有物。** 実装 PR の差分にこれらの変更が
  含まれていたら `ESCALATE`（正典の書き換え）。振る舞いを変えたいなら、先に仕様の PR を出す。
- 仕様の PR（`specs/` と constitution だけを変える立法の PR）は**判事の審査対象ではない**。承認するのは
  人間のマージ。仕様の PR に招集されたら、判定を出さず「立法は審査対象外」と返す。
- `plan.md` の変更は、それ自体では違反にしない。ただし設計が契約から逸れていないかを
  セマンティックチェックで確かめ、所見に書く。
- `tasks.md` の変更（`[X]` の付与、`/speckit-converge` が追記する Convergence フェーズ）は行政の
  作業記録なので想定内。

`judge.md` の「製品仕様 reconcile の検査」（`product_spec` / `docs/specs/`）は `goals/` 契約用。
spec-kit の契約では、上のとおり「仕様が先にマージされていること」と「実装 PR が正典を変えていないこと」で
同じ目的（仕様を腐らせない）を担保する。

## スコープ

契約外の変更の判定には、`tasks.md` のタスクが指すファイルと `plan.md` の構成を境界の目安にする。
そこから外れる変更は「スコープ逸脱」の候補としてセマンティックに検討する（目安であって機械的な
禁止ではない。テストやフィクスチャの追加は通常スコープ内）。

## 検証サーフェス

spec-kit に「検証サーフェス」の宣言は無い。`judge.md` の手順どおり、`git diff` の対象パスから**推定**する。
