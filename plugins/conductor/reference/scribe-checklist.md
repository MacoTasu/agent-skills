# 書記に依頼するときの一覧（渡すもの・観点）

指揮が書記（レビューの観点ごとに所見を出す役。判定はしない）に依頼するときの一覧。
**書記を招集する指揮は、招集の前にこのファイルを Read し、この一覧に従う**（`SKILL.md`「レビュー招集ルール」、`parent-child.md`「実装から PR まで」の 2.、
`claude -p` で回すときは `headless-backend.md`「書記（Task を呼べない指揮のとき）」）。

書記についての決まりは、`SKILL.md`「レビュー招集ルール」「ドメイン招集ルール」「公式プラグインへの委譲の書き方」、
`parent-child.md`、`headless-backend.md`、`codex-backend.md` に分かれて書かれている。
このファイルはそれを 1 か所に集めたもの。各行の「元の場所」が出どころ。

- **「元の場所」が書かれた行**は写し。食い違ったら、元の手順書（`SKILL.md`・`parent-child.md` など）が正。このファイルのほうを直す。
- **「元の場所」が書かれていない行**（あとからこのファイルに足された行）は、このファイルが正。

招集の仕方（Task での直接起動、`subagent_type` と `model` の値）は `SKILL.md`「レビュー招集ルール」「モデル階層ポリシー」に書いてあり、ここには写さない。

> **振り返り（retro）の提案の置き場。** レビューの観点が所見として拾うべきだったもの（retro の層 `書記`。`dev-crew` 同梱 `agents/retro.md` の
> 「チェックリスト」）への手当ては、この一覧の行として足す。足す・変えるのは、人間がこのファイルへの変更をマージしたときだけ。
> どの種類の手当てがどこに着地するかの索引は、`dev-crew` 同梱 `reference/failure-criteria.md`「着地の索引」。

## 渡すもの

| 渡すもの | 中身 | 元の場所 |
|---|---|---|
| 実装のある場所 | 子は worktree の中で書記を招集する（書記が実装のある場所を見るように） | `parent-child.md` 冒頭、「実装から PR まで」の 2. |
| `model` | 観点ごとの値を明示して上書きする | `SKILL.md`「レビュー招集ルール」「モデル階層ポリシー」 |
| ドメイン知識パックの場所 | `dev-crew:domain-architect` には `.claude/skills/<domain>/`（references / checklists）を引数で明示して渡す。パックが無ければ汎用観点のみで判断させ、「ドメイン知識不足」を明示させる | `SKILL.md`「ドメイン招集ルール」の 1. |
| 適用する skill | プロダクト観点（`saas-review` / `architecture-review`）は agent ではなく skill なので、Task のサブエージェントに当該 skill を適用させて所見を出させる | `SKILL.md`「プロダクト観点の追加招集」 |

### `claude -p` で回すときだけ（指揮が Task を呼べないとき）

指示文に書くこと。元の場所はどれも `headless-backend.md`「書記（Task を呼べない指揮のとき）」。
Task で招集するときに差分の範囲・契約をどう渡すかは、いまの決まりには書かれていない。

| 渡すもの | 中身 | 元の場所 |
|---|---|---|
| 差分の範囲と契約 | 差分の範囲（例: `origin/main...HEAD` と未コミットの変更）と契約 | 同節の 1. |
| 書かせないこと | リポジトリ内のファイルを作らない・変更しない・コミットしない | 同節の 3. |
| 所見の形 | 各観点の所見を観点ごとに見出しを分けて、そのまま最終応答に並べる（束ねて判定しない。判定は判事）。招集できなかった観点は「未取得（理由）」と書く | 同節の 4. |

## 観点

| 観点 | いつ招集するか | 見るもの | 元の場所 |
|---|---|---|---|
| `pr-review-toolkit:comment-analyzer` | レビューのとき（差分の性質に無関係なら省く） | 機械的なコメント整合チェック | `SKILL.md`「レビュー招集ルール」、見るものは「モデル階層ポリシー」の表の「根拠」の列 |
| `pr-review-toolkit:code-simplifier` | 同上 | 機械的な簡素化 | 同上 |
| `pr-review-toolkit:pr-test-analyzer` | 同上 | 限定推論(テスト網羅性) | 同上 |
| `pr-review-toolkit:silent-failure-hunter` | 同上 | 限定推論(握り潰し検出) | 同上 |
| `pr-review-toolkit:type-design-analyzer` | 同上（型の変更が無ければ省く） | 限定推論(型設計) | 同上 |
| `pr-review-toolkit:code-reviewer` | 同上 | 限定推論(品質一般) | 同上 |
| `dev-crew:business-reviewer` | ビジネス / 要件 / 優先度 / スコープ / ステークホルダー影響の論点があるとき | 左の論点 | `SKILL.md`「レビュー招集ルール」 |
| `dev-crew:domain-architect` | ドメインモデル / ユビキタス言語 / 境界づけられたコンテキストの論点があるとき | 左の論点 | 同上、「ドメイン招集ルール」 |
| `saas-review` skill | 差分がマルチテナント / 課金・プラン / 権限・招待 / 退会・削除 / マスターデータを含むとき | テナント境界・課金の冪等性・監査証跡・論理削除とマスキング・個社要件の混入 | `SKILL.md`「プロダクト観点の追加招集」 |
| `architecture-review` skill | 差分がメール送信・決済・通知などの外部API / 非同期ジョブ・キュー / DB マイグレーション / API レスポンス型変更を含むとき | outbox・部分失敗・冪等性・順序保証・後方互換・可観測性 | 同上 |
| `codex-review` | 対象リポジトリの `.claude/conductor.json` の `scribes` にあるとき | Codex 自身のコードレビュー | `SKILL.md`「別ベンダーの所見(任意)」、`codex-backend.md`「書記の手順」 |

## 招集するときの決まり

| 決まり | 元の場所 |
|---|---|
| 独立した観点は、同一ターンで Task を一括並列に起動する | `SKILL.md`「レビュー招集ルール」「プロダクト観点の追加招集」 |
| 全観点を毎回回す必要はない。差分の性質に無関係な観点は省く | `SKILL.md`「プロダクト観点の追加招集」 |
| プロダクト観点は無条件には回さない（該当しない差分で回すと指摘がノイズで埋まる） | 同上 |
| `feature-dev` / `pr-review-toolkit` / `commit-commands` が未導入なら、招集を試みずその場で止まり導入を促す | `SKILL.md` 冒頭「前提プラグインの検査」 |
| 任意（`frontend-design` `code-simplifier` `saas-review` `architecture-review`）は、無ければ観点をスキップし「未確認」と明示する（黙って省かない） | 同上、`SKILL.md`「プロダクト観点の追加招集」 |
| implement フェーズなら、Plan を提示する前に `dev-crew:domain-architect` の所見を反映する | `SKILL.md`「ドメイン招集ルール」の 2. |
| code-reviewer 系を回した後、追加で回すのは domain / business 観点だけ。コード品質の二重レビューはしない | `SKILL.md`「公式プラグインへの委譲の書き方」の 3. |
| `codex-review` が前提の欠落や失敗で取れなければ「Codex レビュー: 未取得（理由）」と明記して進む（書記の失敗で判事を止めない） | `SKILL.md`「別ベンダーの所見(任意)」、`codex-backend.md`「書記の手順」 |
| 所見は、司法に渡す証拠 (c) に含める。書記に拘束力は無く、束ねて判定するのは判事 | `SKILL.md`「プロダクト観点の追加招集」「司法ゲート(判事・拘束力ある最終判定)」 |
| 各観点の生レポートを連結して丸投げしない | `SKILL.md`「司法ゲート(判事・拘束力ある最終判定)」「アンチパターン」 |
