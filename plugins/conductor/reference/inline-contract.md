# インライン契約のテンプレート

仕様を作らない小さな変更で、子（worktree の `/conductor:dev`）が Plan Mode で人間と合意する契約の書き方。
**契約を書く役は、Plan Mode に入る前にこのファイルを Read し、この書き方で書く**（`SKILL.md`「大原則」、`parent-child.md`「種別: インライン契約（Plan Mode）」の 1.）。

インライン契約についての決まりは、`SKILL.md`・`parent-child.md`・`codex-backend.md`、`dev-crew` 同梱 `skills/implement/SKILL.md`、
`review-judge` 同梱 `agents/judge.md`・`reference/verification-surfaces.md` に分かれて書かれている。
このファイルはそれを 1 か所に集めたもの。各項目の末尾の（）が元の場所。

- **元の場所が書かれた項目**は写し。食い違ったら、元の手順書（`SKILL.md`・`parent-child.md` など）が正。このファイルのほうを直す。
- **元の場所が書かれていない項目**（あとからこのファイルに足された項目）は、このファイルが正。

> **振り返り（retro）の提案の置き場。** `dev-crew` 同梱 `agents/retro.md` の「契約テンプレート」のうち、ハーネス側のものはこのファイル。
> 契約に必ず書く基準・検証方法を足す・変えるのは、人間がこのファイルへの変更をマージしたときだけ。
> どの種類の手当てがどこに着地するかの索引は、`dev-crew` 同梱 `reference/failure-criteria.md`「着地の索引」。

## いつ使うか

- **仕様を作らない小さな変更**（typo・1箇所のバグ修正など）に使う。機能追加・振る舞いの変更は spec-kit の仕様を先に PR にする
  （`SKILL.md`「大原則」の「立法(契約)は2種類」）。
- どちらに当たるかは「振る舞いが変わるか」で決め、迷えば人間に 1 問だけ聞く（`parent-child.md`「入口」）。
- 合意を取るのは子。親は Plan Mode に入らず、**完了基準を先取りして書かない**（`SKILL.md`「大原則」、`parent-child.md`「依頼ファイル（親が書く）」）。

## 書くもの

```
## 契約

| # | 完了基準 | 検証方法（実行コマンド） |
|---|---|---|
| C1 | <満たされたと言える状態> | `<そのまま実行するコマンド>` |
| C2 | … | `…` |

## 検証サーフェス
<この変更が触れる接触面。書かなければ司法が差分から推定する>
```

- **完了基準ごとに、検証方法（実行コマンド）を併記する**（`SKILL.md`「大原則」、`parent-child.md`「種別: インライン契約（Plan Mode）」の 1.）。
  検証方法の無い基準があると、司法は `RETRY` にする（`review-judge` 同梱 `agents/judge.md`「入力と SSOT 分離」）。
- 検証方法は、行政が 1 対 1 で実行し（`dev-crew` 同梱 `skills/implement/reference/post-checks.md`「インライン契約」）、
  司法が自分の決定性チェックに 1 対 1 で対応づける（同 `agents/judge.md`「入力と SSOT 分離」）。
  判事が Codex のときは、指揮が**そのまま**実行して生の出力を基準ごとに保存する（`codex-backend.md`「1. 決定性チェックを指揮が実行する」）。
- **「## 検証サーフェス」の宣言**は、あれば司法がそれを読み、無ければ `git diff` の対象パス・拡張子から推定する
  （同 `agents/judge.md`「サーフェス照合(検証不足の検知)」の 2.）。サーフェスごとに要る証拠の種類は
  `review-judge` 同梱 `reference/verification-surfaces.md` の表にあり、**具体的なコマンドは検証方法の欄に書く**（同ファイル）。
- 契約に制約（ガードレール）を書いたとき、それに抵触する変更は司法が `ESCALATE` にする（同 `agents/judge.md`「判定スキーマ(型付き4値・必ずどれか1つ)」）。

## 承認を求める前に確かめること

契約を書く役が、契約を人間に提示する前に行う。元の場所は無い（このファイルが正）。
各項目の末尾の括弧書きは、`dev-crew` 同梱 `reference/failure-criteria.md` の基準と、出典の課題番号。`<基点>` は `git merge-base origin/main HEAD`（PR の向き先が `main` でなければ、その枝）。

1. **検証コマンドを、変更前のツリーで 1 度実行する。** 見るのは 4 つ: 実行できる（`command not found`・終了コード 127 にならない）／
   期待値（件数など）を書いたなら、いまの実測から、変更後にその値になる理由を説明できる（いまの時点で期待値どおりなら、その式は変更を確かめていない。
   「変わらないこと」を確かめる式は、いまの実測が期待値と同じ）／`grep -A<N>`・`head` などで出力を切るなら、確かめたい行が出力に残る／
   同じ事項を述べる契約のほかの行と食い違わない。固定文字列の検索は `grep -F` で書く。
   Plan Mode の中で実行できないコマンド（書き込みを伴うもの。2. の worktree を作る手順を含む）は、検証方法の欄に「未実行（理由）」と書き、
   承認のあと、行政に渡す前に、契約を書いた役が最初に実行する。そこで成り立たなければ、行政に渡さず人間に伝える。（`unreliable-check` #23）
2. **判定（テスト・検査）を足す・変える変更には、「その判定が、直す前のツリーで失敗する」を完了基準の 1 行にする。**
   検証方法は、作業ツリーを書き換えない形で書く（司法も同じコマンドを実行する。`git checkout <基点> -- <ファイル>` や `git stash` で戻す形にしない）:
   `git worktree add --detach <一時ディレクトリ> <基点>` → 足した・変えた判定のファイルだけをそこへコピー → その中で判定を実行して失敗を見る →
   `git worktree remove --force <一時ディレクトリ>`（消すのは、自分が作った一時ディレクトリだけ）。（`unreliable-check` #48）
3. **「断られる／通る」を確かめる基準には、空振りしないことの確かめを併記する。** 前提（認証・設定・規則）をわざと壊すと検査が落ちること、
   または反対側の入力で結果が変わること。状態コードだけで判定せず、断られた理由まで見る。（`unreliable-check` #91）
4. **依頼が下の表の種類に当たるかを 1 行ずつ見て、当たる行の確かめ方を、完了基準と検証方法に書く。** 当たらない行は書かない。（`missing-check-form`）

| 要件の種類 | 契約に書く確かめ方 | 出典 |
|---|---|---|
| 値が 0／空になる | 共有環境の残りに依存しない空の状態を作り、絶対値で確かめる（前後の差だけを見るテストは数えない）。作れないなら、どう確かめるかを契約で合意する | #58 |
| 何かを外す・消す | 外れた結果を実際の値で確かめる（見た目なら `getComputedStyle` / `toHaveCSS` などの computed style。クラスや分岐の有無だけでは数えない） | #60 |
| 文字列の解析・抽出・除去 | 境界の入力を並べた表駆動テスト（全角の文字が隣接する、大文字小文字・エンコードの表記ゆれ、接頭辞の別形）。表の行数を完了基準に書く | #59 |
| 定期的に走る・常駐する処理 | 同じ入力で 2 回続けて走らせ、作成物・コメント・ラベルの件数が 1 回目と同じ／2 本を同時に走らせ、副作用が 1 本分だけ（ロックの有無と限界を書く） | #83 |
| 既存と意味が重なるパラメータを足す | 両方が同時に指定されたときの結果（どちらが勝つか・無視するか）と、それを確かめるテスト | #56 |
| 外部の CLI をバックグラウンドで起動する手順 | 起動前の認証の確認／生死の確認／終了コードの記録と検査の順序（失敗したら成果物を作らない）、の 3 つが手順に在ること | #37 |

## 合意のあと

| 場面 | 決まり | 元の場所 |
|---|---|---|
| 記録 | リポジトリのファイルには残さない。PR 本文に「契約」節として、**合意した完了基準と検証方法をそのまま貼る**（記録はこれだけ） | `SKILL.md`「大原則」、`parent-child.md`「種別: インライン契約（Plan Mode）」の 1.・3. |
| 行政に渡す | `dev-crew:implement` に契約を渡す。行政は契約を確認し、曖昧・欠落があれば着手せず指揮に差し戻す。差分は契約のスコープ内に保つ | `parent-child.md`「実装から PR まで」の 1.、`dev-crew` 同梱 `skills/implement/SKILL.md`「手順（インライン契約）」 |
| 司法に渡す | 招集時の引数 (a) として、合意した完了基準と検証方法を**そのまま**渡す。契約が渡されなければ、司法は推測で補わず `RETRY` にする | `SKILL.md`「大原則」「司法ゲート(判事・拘束力ある最終判定)」の 1.、`review-judge` 同梱 `agents/judge.md`「入力と SSOT 分離」 |
| 範囲が変わった | 「ついでにこれも」「この要件は無しで」と言われたら、実装を止め、**Plan Mode をやり直して新しい契約**の承認を得る。以後は新しい契約で行政から進める | `parent-child.md`「人間が子に直接指示するとき」 |
| 単発のレビュー | 契約の代わりにレビュー基準を (a) として渡す | `SKILL.md`「司法ゲート(判事・拘束力ある最終判定)」の 1. |
