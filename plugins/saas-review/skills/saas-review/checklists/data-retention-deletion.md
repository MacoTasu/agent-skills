# データ保持・削除・エクスポート

status: draft

差分に退会処理 / 削除処理 / 新規テーブル・カラム追加 / 外部サービスへのデータ同期 が
含まれるときに読む。

---

## 退会時の削除範囲と猶予期間

- **なぜ危険か**: 即時物理削除は誤操作からの復旧を不可能にし、逆に何も消えなければ
  個人情報が無期限に残留する。どちらも後から直すのが極めて高くつく。
- **どう検出するか**: 退会処理が soft delete か hard delete かをコードで確認する。
  soft delete なら、猶予期間経過後に実際に物理削除するジョブが存在するかを
  `grep -rn "deleted_at"` と cron / worker 定義の両方から確認する。
- **よくある間違った実装**: `deleted_at` を立てる実装だけがあり、実際に消すジョブが
  どこにも存在しない。「論理削除しています」と説明できるが、実態は無期限保持。

## 削除の波及（外部サービスを含む）

- **なぜ危険か**: 自社 DB からは消えても、決済事業者・検索インデックス・オブジェクト
  ストレージ・メール配信基盤・分析基盤に残る。「削除しました」という顧客への説明が
  事実と食い違う。
- **どう検出するか**: 差分でデータを外部に送っている箇所を列挙し
  （`grep -rniE "stripe|algolia|meilisearch|sendgrid|resend|bigquery|s3|r2"`）、
  それぞれに対応する削除経路が存在するかを確認する。
- **よくある間違った実装**: 分析基盤への同期が一方向で、削除が伝播する経路が最初から無い。

## エクスポート（データポータビリティ）

- **なぜ危険か**: 要求されてから手作業で組むことになり、契約上の期限に間に合わない。
  手作業は漏れと誤送信のリスクも伴う。
- **どう検出するか**: 差分で新テーブル・新カラムが追加されていたら、エクスポート処理の
  対象に含まれているかを確認する。エクスポートがテーブル名のハードコード列挙になっていれば、
  新規テーブルは必ず漏れるので指摘する。
- **よくある間違った実装**: エクスポート実装が作った当時のテーブル一覧で固定されていて、
  追加分が自動的に漏れ続ける。

## バックアップの保持期間と削除ポリシーの整合

- **なぜ危険か**: 「削除した」と説明した後もバックアップに残り続けると、説明と実態が
  食い違う。開示請求や監査で問題になる。
- **どう検出するか**: バックアップの保持期間が文書化されているか、それが削除ポリシーの
  猶予期間と整合しているかを確認する。文書が無ければそれ自体を指摘する。
- **よくある間違った実装**: 無期限バックアップを取り続け、誰もその存在を削除ポリシーと
  突き合わせていない。

## ログ・分析データに残る個人情報

- **なぜ危険か**: 本体データを消してもログに残っていれば、個人情報は削除されていない。
  ログは保持期間が長く、アクセス権も広い。
- **どう検出するか**: 差分の新規ログ出力・イベント送信に、メールアドレス・氏名・
  電話番号・住所が含まれていないかを確認する。含まれるなら ID に置き換えられないか検討する。
- **よくある間違った実装**: 分析イベントに「わかりやすいから」とメールアドレスを
  識別子として送る。
