## 物理削除と論理削除の使い分け

- **なぜ危険か**: 日常操作で物理削除すると、誤操作からの復旧も「誰が何を消したか」の追跡も
  不可能になる。逆にすべてを論理削除にすると、保持期間を過ぎた個人情報が無期限に残り続け、
  削除要求に応えられなくなる。**どちらか一方に倒した設計はどちらの事故も防げない**。
- **どう検出するか**: 差分の削除処理が物理削除（`DELETE FROM` / `.delete()` / `destroy`）か
  論理削除（`deleted_at` / `status = 'deleted'`）かを確認する。物理削除なら、それが
  ライフサイクル終端（退会・保持期間満了のバッチ）に限定されているかを確認する。
  論理削除なら、削除後もレコードを辿れるか（外部キーや一覧クエリから消えるだけで、
  監査目的では参照できるか）を確認する。
- **よくある間違った実装**: 一覧から消せばよいという理由で日常操作に物理削除を使う。
  逆に、論理削除を入れたが最終的に物理削除へ到達する経路がどこにも存在しない。

## マスターデータの版管理と過去レコードの再現性

- **なぜ危険か**: 料金表・税率・プラン定義・商品マスタ・権限定義といったマスターを
  上書き更新すると、**過去の取引や操作を当時の定義で再現できなくなる**。請求額の根拠を
  問われた時に説明できず、監査でも再計算でも詰む。しかも壊れたことに気づくのは、
  マスタを変更してから数か月後。
- **どう検出するか**: 差分がマスターデータのテーブル・定義ファイルに触れているか確認する。
  触れているなら、(1) 履歴を持つ設計か（バージョン列 / 有効期間 `valid_from`・`valid_to` /
  履歴テーブル）、(2) 明細側が「マスタへの参照」ではなく「適用時点の値のコピー」または
  「マスタの版への参照」を持っているか、を確認する。
  `grep -rniE "valid_from|effective_|version|_history"` で履歴設計の有無を見る。
- **よくある間違った実装**: 請求明細が `price_id` だけを持ち、マスタ側の価格を書き換えた
  結果、過去の請求書を表示すると新価格で表示される。

## 保持期間の根拠と、削除要求との衝突の解決

- **なぜ危険か**: 「なんとなく全部残す」「なんとなく一定期間で消す」のどちらも、
  法令上の保持義務（取引記録・帳簿類は年単位の保存が要求される）と、個人情報の
  「目的達成後は保持しない」原則の**両方を同時に破りうる**。一律の期間設定は、
  どちらか一方には必ず違反する。
- **どう検出するか**: 差分で新しいデータ種別が増えたら、その種別の保持期間と根拠
  （法令・契約・運用要件のどれか）が文書化されているかを確認する。文書が無ければ
  それ自体を指摘する。既に保持期間が定義されている場合、ユーザーからの削除要求が来た時に
  「保持義務のある種別は残し、それ以外は消す」という選別ができる粒度になっているかを見る。
- **よくある間違った実装**: 全テーブル一律の保持期間を設定する。取引記録には短すぎ、
  個人情報には長すぎる、という両方向の違反になる。

## 退会・解約時に消し切れるか（外部サービスを含む）

- **なぜ危険か**: 自社 DB から消えても、決済事業者・検索インデックス・オブジェクト
  ストレージ・メール配信基盤・分析基盤に残る。「削除しました」という顧客への説明が
  事実と食い違い、開示請求や監査で問題になる。
- **どう検出するか**: 差分でデータを外部に送っている箇所を列挙し
  （`grep -rniE "stripe|algolia|meilisearch|sendgrid|resend|bigquery|s3|r2"`）、
  それぞれに対応する削除経路が存在するかを確認する。退会処理のコードを起点に、
  自社 DB 以外に到達しているかを追う。
- **よくある間違った実装**: 分析基盤への同期が一方向で、削除が伝播する経路が最初から無い。

## バックアップからの復元可能性と、完全削除との両立

- **なぜ危険か**: 法令対応や事故対応のためにスナップショットからの復元が必要な一方、
  「完全に削除した」と説明したデータがバックアップに残り、復元すると**消したはずのデータが
  蘇る**。この矛盾を設計で解いていないサービスは、どちらかの説明が必ず嘘になる。
- **どう検出するか**: (1) バックアップ／スナップショットの保持期間が文書化され、削除
  ポリシーと突き合わされているか、(2) **復元手順が実在し、実際に試されたことがあるか**
  （手順書だけで一度も実行していないものは動かないと見なす）、(3) 復元後に、削除済み
  対象を再削除する手順が定義されているか。
- **よくある間違った実装**: 無期限スナップショットを取り続け、削除ポリシーと一度も
  突き合わせていない。あるいは復元手順が存在せず、「バックアップはある」だけで
  復元できると信じている。

## エクスポート（データポータビリティ）

- **なぜ危険か**: 要求されてから手作業で組むことになり、契約上の期限に間に合わない。
  手作業は漏れと誤送信のリスクも伴う。
- **どう検出するか**: 差分で新テーブル・新カラムが追加されていたら、エクスポート処理の
  対象に含まれているかを確認する。エクスポートがテーブル名のハードコード列挙になっていれば、
  新規テーブルは必ず漏れるので指摘する。
- **よくある間違った実装**: エクスポート実装が作った当時のテーブル一覧で固定されていて、
  追加分が自動的に漏れ続ける。

## ログ・分析データに残る個人情報

- **なぜ危険か**: 本体データを消してもログに残っていれば、個人情報は削除されていない。
  ログは保持期間が長く、アクセス権も広い。
- **どう検出するか**: 差分の新規ログ出力・イベント送信に、メールアドレス・氏名・
  電話番号・住所が含まれていないかを確認する。含まれるなら ID に置き換えられないか検討する。
- **よくある間違った実装**: 分析イベントに「わかりやすいから」とメールアドレスを
  識別子として送る。
