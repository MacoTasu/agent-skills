# 外部連携とトランザクション整合

status: draft

差分に外部 API 呼び出し（メール送信 / 決済 / 通知 / 検索インデックス更新 / 自社が送る
webhook）/ 非同期ジョブ / メッセージキュー が含まれるときに読む。

---

## DB トランザクションと外部副作用の二重書き込み（outbox）

- **なぜ危険か**: DB のトランザクションはロールバックできるが、**送信済みのメールも、
  実行済みの決済も取り消せない**。トランザクション内で外部を呼べばロールバック時に
  外部だけ実行済みになり、コミット後に呼べば送信前に落ちた時に永久に送信されない。
  この二重書き込み（dual write）は必ずどちらかに倒れる。しかも失敗は低頻度でしか
  起きないためテストでは再現せず、本番で一部のユーザーにだけ起きて追跡もできない。
- **どう検出するか**: 差分のトランザクション境界（`transaction(` / `BEGIN` / `tx.` /
  `db.$transaction`）の内側に外部呼び出しが含まれていないかを確認する
  （`grep -rniE "sendgrid|resend|nodemailer|sendMail|stripe|slack|fetch\(|http\."` と
  トランザクション範囲を突き合わせる）。含まれる場合、**outbox になっているか**
  ——同一トランザクションで「送るべきこと」を行として記録し、別プロセスがそれを読んで
  送信し、送信済みを記録する形か——を確認する。outbox でないなら最低限、コミット後に
  送信し、**送信失敗が記録として残って再送できる**形になっているかを見る。
- **よくある間違った実装**: `await db.transaction(async (tx) => { ...; await sendMail(); })`。
  あるいはコミット直後に送信して失敗をログに出すだけ（ログは再送の材料にならないので、
  実質「送られなかったことが誰にも分からない」）。

## 部分失敗の後始末（外部は成功・自DBは失敗）

- **なぜ危険か**: 外部呼び出しが成功した直後に自 DB の記録で失敗すると、**ユーザーは
  課金されたのにサービス側に記録が無い**という最悪の不整合になる。リトライすれば
  二重実行、放置すれば消えた取引。
- **どう検出するか**: 外部呼び出しと DB 書き込みの順序を読み、「外部 → DB」の順なら
  DB 側が失敗した時の補償があるかを確認する（記録の再試行、外部側 ID を先に予約しておく、
  定期の照合バッチ）。照合バッチがある場合、その突き合わせ対象に今回の新しい処理が
  含まれるかも見る。
- **よくある間違った実装**: 決済成功後の DB 保存で落ち、ユーザーには課金されたが未反映。
  照合する手段が無いので、問い合わせが来るまで誰も気づかない。

## リトライと冪等性

> 公式 `silent-failure-hunter` が「エラーを握り潰していないか」を見るのに対し、
> ここは「**再実行されても壊れないか**」を見る。視点が違うので両方必要。

- **なぜ危険か**: キュー・webhook・ジョブは at-least-once が基本で、必ず再実行される。
  冪等でない副作用は二重登録・二重課金・二重通知になる。
- **どう検出するか**: 差分の非同期ジョブ / webhook ハンドラ / 決済呼び出しについて、
  冪等キーまたは重複検知（ユニーク制約・処理済みテーブル・状態遷移ガード）があるかを確認する。
- **よくある間違った実装**: at-least-once の配信保証を at-most-once だと思い込み、
  「基本的に1回しか来ない」前提で副作用を書く。

## 順序保証への暗黙の依存

- **なぜ危険か**: キューやイベント配信の多くは順序を保証しない。更新イベントが逆順で
  届くと、**古い値が新しい値を上書きして巻き戻る**。データは壊れているが例外は出ないので、
  誰も気づかないまま蓄積する。
- **どう検出するか**: 差分でイベント／メッセージを送信・受信している箇所に、版を表す情報
  （`version` / `updated_at` / シーケンス番号）が載っているかを確認する。受信側が
  「自分が持つ版より古いイベントを捨てる」判定をしているかを見る。
- **よくある間違った実装**: 「送った順に届く」前提で、受信したペイロードをそのまま
  上書き保存する。

## 外部依存の障害が自サービスの可用性に直結していないか

- **なぜ危険か**: ユーザー操作のクリティカルパスで外部 API を同期的に待つと、その外部が
  落ちた瞬間に自サービスも落ちる。自分では復旧できない障害を抱え込むことになる。
- **どう検出するか**: 差分の外部呼び出しが、ユーザーのリクエストを完了させる条件に
  なっているかを確認する。非同期（キュー投入して即応答）にできないか、失敗時の
  フォールバックがあるかを見る。
- **よくある間違った実装**: サインアップ完了の条件にウェルカムメールの送信成功を含め、
  メール基盤の障害でサインアップ自体ができなくなる。
