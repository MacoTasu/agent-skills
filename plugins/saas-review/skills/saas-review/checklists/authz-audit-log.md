# 権限(RBAC)・監査ログ

status: draft

差分にエンドポイント追加 / ロール判定 / 招待・メンバー追加 / ロール変更 / メンバー削除 /
ログ出力 が含まれるときに読む。

---

## 認可のデフォルトが deny か allow か

- **なぜ危険か**: デフォルト allow のルーティングでは、新しいエンドポイントを追加した時の
  「認可の付け忘れ」が無言で成立する。レビューで気づかなければ誰も気づかない。
- **どう検出するか**: 差分で追加されたルートが、認可ミドルウェア／デコレータの適用範囲に
  入っているかを確認する。ルータ定義を開き、認可が「明示的に付けたものだけ適用」なのか
  「明示的に外したものだけ除外」なのかを判定する。
- **よくある間違った実装**: 公開エンドポイント用に用意した `publicRouter` に、うっかり
  認証必須のハンドラを追加する。

## ロール昇格経路

- **なぜ危険か**: メンバー招待やロール変更 API で自分より上位のロールを付与できると、
  一般メンバーが owner に昇格でき、RBAC の設計全体が無意味になる。
- **どう検出するか**: ロールを書き込む処理を列挙し、「呼び出し元のロール ≥ 付与しようとする
  ロール」の検証があるかを確認する。招待の受諾処理側でロールが再検証されるかも見る。
- **よくある間違った実装**: owner 判定を「メンバーが1人のとき」などの暗黙条件で代用し、
  メンバーが増えた時に成立しなくなる。

## 監査ログの記録対象

- **なぜ危険か**: 事故発生後に「誰が何をいつやったか」を再現できない。顧客説明ができず、
  セキュリティ要件（SOC2 等）のある顧客には売れなくなる。
- **どう検出するか**: 差分が権限変更 / データ削除 / エクスポート / 課金変更 のいずれかに
  触れているなら、監査ログ書き込みがあるかを確認する。ログに actor / 対象 / 変更前後 /
  時刻 / IP が含まれるか。
- **よくある間違った実装**: アプリログ（標準出力）で代用する。保持期間が数日しかなく、
  問題が発覚した頃には消えている。

## 監査ログへの機微情報の混入

- **なぜ危険か**: ログ基盤は権限設計がアプリより緩いことが多く、そこに個人情報や
  トークンを流すと、ログ基盤自体が新しい漏洩面になる。
- **どう検出するか**: 差分の追加ログ出力の引数を確認する。リクエストボディやヘッダを
  丸ごと渡している箇所（`log(req)` / `JSON.stringify(body)`）を grep で探す。
- **よくある間違った実装**: 障害調査のためエラー時だけリクエスト全体を出力し、そのまま残す。

## メンバー削除・退職後のアクセス失効

- **なぜ危険か**: membership 行を消しただけでは、既存セッション・API キー・未使用の招待
  リンクが生き続ける。退職者がアクセスできる状態は監査で必ず問題になる。
- **どう検出するか**: メンバー削除処理を読み、セッション失効・API キー無効化・招待取り消しまで
  到達しているかを確認する。セッションが JWT なら、失効手段（短い有効期限 or 失効リスト）が
  あるか。
- **よくある間違った実装**: DB の membership 行を削除するだけで完了とする。
