# 個社要件と汎用性（プロダクト境界）

差分に特定顧客の要望に由来する機能 / 条件分岐つきの挙動 / 設定項目の追加 が
含まれるときに読む。

---

## 個社要件がプロダクトのコアに混入していないか

- **なぜ危険か**: 特定顧客のための分岐がコアに入ると、以後すべての変更がその顧客の
  ケースを考慮する必要が生じ、**変更コストが恒久的に上がる**。しかも入れた分岐は
  誰も消せない（壊れるかもしれないので）。SaaS が受託開発に変質していく最も一般的な経路で、
  1件ずつは小さいため、レビューで止めない限り必ず通る。
- **どう検出するか**: 差分に特定顧客・特定テナントを識別する条件が無いかを確認する
  （`grep -rniE "if.*(tenant|org|company|customer)_?id ==|=== ['\"][a-z0-9-]{8,}"`、
  顧客名・社名を含む識別子、`isSpecialCase` 系のフラグ）。
  条件分岐が見つかったら、それが**プロダクトの概念として名前を持てるか**を問う
  （「A社向け」ではなく「請求書を月次でまとめる運用」のように、他社にも売れる形で
  説明できるか）。説明できないなら個社要件。
- **よくある間違った実装**: 「今はこの1社だけだから」とテナント ID の直接比較を入れる。
  半年後には同じ形の分岐が5個に増えている。

## 外に切り出せる機能をコアに抱え込んでいないか

- **なぜ危険か**: 一部の顧客しか使わない機能をコア製品に持つと、全顧客がその複雑さの
  コスト（UI の項目、設定、障害面、テスト時間）を払う。逆に、外部アプリケーション
  （連携・拡張・別プロダクト）として切り出せば、コアは単純なまま保て、必要な顧客だけが
  導入し、独立して課金・提供できる。
- **どう検出するか**: 追加された機能について次を確認する。(1) 全テナントのうち使うのは
  何割の想定か（ごく一部なら候補）、(2) その機能はコアのデータに**読み書きする API さえ
  あれば外から実現できる**か、(3) コアに入れる場合に、コア側のドメインモデルへ
  新しい概念を追加する必要があるか（必要なら、それが本当にプロダクトの概念か）。
  (1)(2) が該当するのに (3) でコアを汚しているなら、外出しを提案する。
- **よくある間違った実装**: 「APIを用意するより直接作ったほうが早い」という理由でコアに
  実装し、結果として外部提供もできず、コアの複雑さだけが増える。
