# 課金・プラン・使用量メータリング

差分に決済 API 呼び出し / プラン判定 / 上限チェック / 使用量の集計・計上 が含まれるときに読む。

---

## 課金イベントの冪等性

- **なぜ危険か**: 決済 webhook は at-least-once で再送される。重複排除が無いと二重課金が起き、
  返金対応と信頼の損失が同時に発生する。金銭が絡むため、事後の「気づかなかった」が通じない。
- **どう検出するか**: 差分の決済 API 呼び出しに idempotency key が渡されているか
  （`grep -rn "idempotency\|Idempotency-Key"`）。webhook ハンドラに受信イベント ID の
  重複排除（DB のユニーク制約や処理済みテーブル）があるか。
- **よくある間違った実装**: ハンドラの処理途中で例外が出ると 200 を返さず再送されるのに、
  「一度しか来ない」前提で副作用を先に実行している。

## プラン制限がサーバ側で効いているか

- **なぜ危険か**: フロントでのみ上限を出し分けている場合、API を直接叩けば上限を超過できる。
  課金回避が可能になり、しかも超過データが正常データとして蓄積する。
- **どう検出するか**: 差分でフロントにプラン分岐（`plan ===` / `isPro` / `canUse`）が
  追加されていたら、対応するサーバ側の作成・更新エンドポイントに同じ判定があるかを確認する。
  無ければ指摘。
- **よくある間違った実装**: UI のボタンを disabled にして実装完了とする。

## ダウングレード・解約時の既存データの扱い

- **なぜ危険か**: 上限を超えたデータが宙に浮き、挙動が未定義になる。黙って削除すれば事故、
  放置すれば課金回避経路になる。
- **どう検出するか**: プラン変更処理に「既存リソース数 > 新プランの上限」の分岐があるか。
  無ければ、その場合の仕様がどこかに書かれているかを確認する（仕様が無いこと自体が指摘）。
- **よくある間違った実装**: 超過分を暗黙に読み取り専用にする実装だけがあり、ユーザーに
  何も通知されず、仕様書にも書かれていない。

## 使用量の計上タイミングと期間の基準

- **なぜ危険か**: 失敗した処理まで計上すると過大請求、月跨ぎの基準がズレると請求額が
  再現不能になる。どちらも問い合わせ対応のコストが跳ね上がる。
- **どう検出するか**: 計上コードが成功パス（トランザクション確定後）にあるか。集計クエリの
  期間境界のタイムゾーンと、請求サイクルの基準タイムゾーンが一致しているか
  （`grep -rn "UTC\|timezone\|startOf"` で確認）。
- **よくある間違った実装**: サーバは UTC、請求サイクルは JST の月初、という不一致を
  誰も検証していない。

## 価格・税率・通貨のハードコード

- **なぜ危険か**: 同じ値がフロントとバックに散り、変更時に片方だけ直して不整合になる。
  表示額と請求額が違うのは最も信頼を失う不具合。
- **どう検出するか**: 差分に金額リテラル・税率リテラル（`0.1` / `1980` / `JPY`）が
  無いか grep する。あれば単一の定義元があるかを確認する。
- **よくある間違った実装**: 税率をフロントの表示計算とバックの請求計算の2箇所に書く。
