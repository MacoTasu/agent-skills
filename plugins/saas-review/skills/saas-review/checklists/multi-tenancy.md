# テナント境界・データ分離

差分にクエリ / RLS ポリシー / キャッシュ / 検索インデックス / オブジェクトストレージ /
バッチ・cron・webhook 受信 が含まれるときに読む。

---

## クエリのテナントスコープ漏れ

- **なぜ危険か**: 1箇所の漏れで他テナントのデータが閲覧・更新・削除される。検知が遅れやすく、
  発覚時には「どのテナントの何が見えたか」の説明責任が発生する。単発で事業を毀損しうる唯一の欠陥。
- **どう検出するか**: 差分の全クエリ発行箇所を列挙する。
  `git diff -U0 | grep -nE "SELECT|INSERT|UPDATE|DELETE|\.from\(|\.query\(|db\."` で拾い、
  各々にテナント識別子の条件があるか確認する。RLS に依存している場合は、対応する
  migration に `CREATE POLICY` があり、かつその接続が RLS を適用されるロールで行われているか
  （service_role / superuser でバイパスしていないか）を確認する。
- **よくある間違った実装**: 共通ヘルパ経由なら安全だと信じて1箇所だけ raw SQL を書く。
  管理画面・集計用のクエリだけ「全テナント見たいから」とスコープを外し、その関数が
  後から通常経路に再利用される。

## ID の推測可能性と IDOR

- **なぜ危険か**: 連番 ID を URL に露出したうえで認可が「レコードが存在するか」しか見ていないと、
  ID を変えるだけで他テナントのリソースを取得できる。攻撃コストがほぼゼロ。
- **どう検出するか**: 差分で追加・変更されたエンドポイントのパス／クエリパラメータを列挙し、
  各々について「リソース取得後にテナント一致を検証しているか」をコードで確認する。
  ハンドラ内に `tenant`/`org`/`workspace` の比較が現れない取得系は疑う。
- **よくある間違った実装**: 404 と 403 を正しく出し分けようとして、テナント検証の前に
  リソースを取得し、存在有無を情報として漏らす。

## バッチ・cron・webhook・管理スクリプトの抜け穴

- **なぜ危険か**: 通常のリクエスト経路には認可ミドルウェアがあるが、非リクエスト経路は
  別の入口であり、そこだけ素通りになる。しかも自動実行なので誰も見ていない。
- **どう検出するか**: 差分に `cron` / `worker` / `job` / `webhook` / `seed` / `scripts/` が
  含まれるか確認し、含まれる場合は「テナントをどう特定しているか」をコードで追う。
  Supabase なら `service_role` キーの使用箇所を `grep -rn "service_role"` で確認し、
  それが本当に管理用途に限定されているか。
- **よくある間違った実装**: 開発時に RLS をバイパスするためサービスロールで書いたコードを、
  そのまま通常処理に昇格させる。

## キャッシュキー・検索インデックスにテナントが含まれない

- **なぜ危険か**: キャッシュ跨ぎで他テナントのデータが返る。再現条件がタイミング依存で、
  テストでは絶対に見つからず、本番で断続的に起きる。
- **どう検出するか**: 差分のキャッシュキー生成箇所（`cache.set` / `redis` / `memo` /
  `revalidateTag` 等）と検索インデックス投入箇所を列挙し、キーにテナント識別子が
  含まれるか目視する。
- **よくある間違った実装**: ユーザー ID は入れたがテナント ID を入れない。ユーザーが複数
  テナントに所属できる仕様になった瞬間に破綻する。

## ファイル／オブジェクトストレージのパスと署名 URL

- **なぜ危険か**: バケットが公開のままだったり、パスが推測可能だったりすると、認証を
  一切通らずにファイルが取得できる。署名 URL の TTL が長いと共有後も生き続ける。
- **どう検出するか**: 差分の upload / download / `getSignedUrl` 呼び出しを列挙し、
  (1) パスにテナント識別子が含まれるか (2) バケットが private か (3) 署名 URL の
  有効期限が用途に対して妥当か を確認する。
- **よくある間違った実装**: 動作確認のため一時的に public bucket にして戻し忘れる。
