# API・スキーマの後方互換と移行

status: draft

差分に API レスポンスの型変更 / DB マイグレーション / 自分が送信する webhook の
ペイロード変更 が含まれるときに読む。

---

## レスポンスの破壊的変更

- **なぜ危険か**: フィールド削除・型変更・optional から required への変更は、古い
  クライアント（特にモバイルアプリや外部連携）を壊す。サーバとクライアントを同時に
  入れ替えられない環境では即障害になる。
- **どう検出するか**: 差分のレスポンス型定義／OpenAPI スキーマを旧版と比較する
  （`git diff origin/main -- '*.ts' '*.go' 'openapi*'`）。フィールドの削除、型の変更、
  optional → required、enum 値の削除・意味の変更を探す。
- **よくある間違った実装**: 「まだ誰も使っていないはず」という推測でフィールドを削除する
  （使用箇所を grep で確認していない）。

## マイグレーションとデプロイ順序（expand / contract）

- **なぜ危険か**: 旧コードが動いている最中にカラム rename や NOT NULL 追加を行うと、
  デプロイ中の数分間に本番が落ちる。ロールバックもできない。
- **どう検出するか**: migration ファイルに `RENAME` / `DROP` / `SET NOT NULL` / 型変更が
  含まれるかを grep する。含まれる場合、「追加 → 両対応で移行 → 削除」の2段階以上に
  分かれているかを確認する。
- **よくある間違った実装**: rename を1つのマイグレーションで完結させ、ローカルで通ったので
  問題ないと判断する。

## 長時間ロックを取るマイグレーション

- **なぜ危険か**: 大きなテーブルへの ALTER やインデックス作成がテーブルロックを取り、
  その間サービス全体が停止する。データ量に比例するため、ローカル検証では絶対に再現しない。
- **どう検出するか**: 対象テーブルの本番行数を確認する。インデックス作成が
  `CREATE INDEX CONCURRENTLY` になっているか、デフォルト値つきカラム追加が使用中の
  DB バージョンで安全か（PostgreSQL 11 未満は全行書き換え）を確認する。
- **よくある間違った実装**: ローカルの数百行で一瞬終わったので本番も一瞬だと判断する。

## ロールバック可能性

- **なぜ危険か**: down migration が無い、またはデータを失う変更だと、問題発生時に
  前に進むしかなくなる。障害対応の選択肢が消える。
- **どう検出するか**: migration に down が定義されているか。down でデータが失われる場合、
  その旨が明記されているか。データを削除・変換する migration では、元に戻せるかを確認する。
- **よくある間違った実装**: down を空で生成したまま放置する。

## 自分が送信する webhook / 外部連携の契約

- **なぜ危険か**: 自社が提供する webhook のペイロードを変えると、受け手の実装が壊れる。
  相手のコードは自分では直せない。
- **どう検出するか**: 差分に webhook ペイロード生成箇所が含まれるかを確認し、含まれる場合は
  フィールドの削除・改名が無いか、ペイロードにバージョンが付いているかを確認する。
- **よくある間違った実装**: 内部のドメインモデルをそのままシリアライズして送っており、
  内部のリファクタリングが外部契約の破壊になる。
