# 観測性と障害時の運用

status: draft

差分に外部 API 呼び出し / 非同期ジョブ / リトライ / 新機能の投入 が含まれるときに読む。

---

## 新しい失敗モードに対する可観測性

- **なぜ危険か**: 追加した処理が壊れていることを、顧客からの問い合わせで初めて知ることになる。
  検知の遅れがそのまま影響範囲になる。
- **どう検出するか**: 差分で追加された外部呼び出し・非同期処理について、失敗時に
  メトリクスまたはアラートに到達する経路があるかを確認する。ログ出力しかない場合、
  そのログを見る仕組み（アラートルール）が存在するかまで確認する。
- **よくある間違った実装**: try/catch でログを出して安心する。そのログは誰も見ていない。

## リトライと冪等性

> 公式 `silent-failure-hunter` が「エラーを握り潰していないか」を見るのに対し、
> ここは「**再実行されても壊れないか**」を見る。視点が違うので両方必要。

- **なぜ危険か**: キュー・webhook・ジョブは at-least-once が基本で、必ず再実行される。
  冪等でない副作用は二重登録・二重課金・二重通知になる。
- **どう検出するか**: 差分の非同期ジョブ / webhook ハンドラ / 決済呼び出しについて、
  冪等キーまたは重複検知（ユニーク制約・処理済みテーブル・状態遷移ガード）があるかを確認する。
- **よくある間違った実装**: at-least-once の配信保証を at-most-once だと思い込み、
  「基本的に1回しか来ない」前提で副作用を書く。

## タイムアウトと同時実行の上限

- **なぜ危険か**: 外部 API が遅くなった時、タイムアウトが無いとワーカーやコネクションが
  占有され、無関係な機能まで巻き込んで全体が停止する。障害が伝播する典型経路。
- **どう検出するか**: 差分の HTTP クライアント生成・呼び出しにタイムアウト指定があるかを
  確認する（`grep -rniE "timeout|deadline|AbortSignal|context.WithTimeout"`）。
  無ければ、そのクライアントのデフォルトが無制限かを調べる。
- **よくある間違った実装**: 言語標準のクライアントをデフォルト設定のまま使う
  （多くの言語でデフォルトは無制限）。

## 相関 ID（テナント・リクエストの追跡）

- **なぜ危険か**: 「特定の顧客だけ遅い / 失敗する」という最も多い問い合わせを調査できない。
  ログはあるのに原因に辿り着けない状態になる。
- **どう検出するか**: 差分で追加されたログが構造化されており、テナント識別子と
  リクエスト識別子をフィールドとして持つかを確認する。非同期ジョブでは、エンキュー元の
  相関 ID が引き継がれているかも見る。
- **よくある間違った実装**: 文字列連結のログを出し、後から絞り込めない。

## 障害時に止める手段（kill switch）

- **なぜ危険か**: 新機能が事故った時、切るのにデプロイが必要だと復旧が数十分単位で遅れる。
  影響が大きい変更ほど、切れないことのコストが高い。
- **どう検出するか**: リスクの高い新機能（外部連携・課金・一斉通知・重い集計）について、
  無効化手段があるかを確認する。環境変数の場合、反映に再起動が必要かどうかまで確認する。
- **よくある間違った実装**: 環境変数で切れるが反映に再デプロイが必要で、結局デプロイと
  同じ時間がかかる。
