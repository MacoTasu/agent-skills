# calendar-tasks

**Google カレンダー 1 本でタスクを管理する。** タスクは接頭辞付きの終日予定、窓口は Claude、毎晩の繰越は routine。
データ（タスク・履歴・設定）は Google カレンダーの中にだけある。

- 予定とタスクを**同じ日付グリッド**で見る。タスク専用アプリを増やさない
- 繰越に人の判断を使わない。未完了は完了か中止になるまで毎営業日動き続ける。判断が要るのは**繰越が多いタスクの見直し**だけ
- 完了は消えない。完了日・初回の予定日・繰越回数・規模が残り、**評価期の振り返り**に使える

## 構成

| ファイル | 役割 |
|---|---|
| `skills/calendar-tasks/SKILL.md` | 窓口。「明日、○○」「○○終わった」を規約どおりの操作に落とす |
| `skills/calendar-tasks/reference/conventions.md` | **規約の唯一の定義**（接頭辞・期限マーク・属性行・設定行・状態遷移・営業日） |
| `skills/calendar-tasks/reference/nightly.md` | 夜間処理の手順書。routine に貼る本文もここ |
| `skills/calendar-tasks/reference/reports.md` | 集計の定義 |

窓口・夜間処理・集計は conventions を参照するだけで、定義を写さない。規約を変えるときは conventions だけを直す。

## 前提

- Google カレンダー連携（claude.ai のコネクタ）が**編集権限で**接続された Claude。claude.ai アプリ、Claude Code のどちらでもよい
- 夜間処理を自動で回すなら、cloud routine（Claude Code の `/schedule`）が使えるプラン
- 対象は既に使っているカレンダー 1 本。新しいカレンダーは作らない
- 想定読者は日本の業務利用（営業日の計算が日本の祝日前提。`skip_holidays=false` にすれば土日だけになる）

## 初期設定

1. **Google カレンダー連携を編集権限で接続する。** claude.ai の設定 → コネクタで Google カレンダーを接続するとき、Google の同意画面で
   「カレンダーの表示、**編集**、共有、削除」にチェックが入っていることを確かめる（表示だけで接続すると、予定の作成が
   `Insufficient scope` で失敗する。その場合は Google アカウント側で Claude のアクセスを取り消してから再接続する）
2. **対象カレンダーを決める。** 仕事用など、タスクを並べたいカレンダー 1 本。そのカレンダーの**タイムゾーンを自分の地域（例: Asia/Tokyo）**にしておく
   （「今日」の判定にカレンダーのタイムゾーンを使う。UTC のままだと朝の操作で「今日」が前日になる）
3. **説明欄に設定行を書く。** Google カレンダーの画面で、そのカレンダーの「設定と共有」→「説明」に 1 行:
   ```
   tasks: due_warn_days=3 skip_holidays=true color=8
   ```
   この行があるカレンダーが対象として認識される。説明欄に既に文章があれば、その末尾に 1 行足せばよい（行頭が `tasks:` の行だけを読む）。
   値を省いた項目は既定値（上の例は全て既定値）。意味は conventions 6 節
4. **窓口を入れる。**
   - Claude Code: `/plugin marketplace add MacoTasu/agent-skills` → `/plugin install calendar-tasks@macotasu-agent-skills`
   - claude.ai アプリ: `skills/calendar-tasks/` フォルダをカスタムスキルとしてアップロードする（`reference/` を含めて 1 フォルダで完結している）
5. **夜間処理を登録する。** `nightly.md` の「routine に保存する本文」を routine のプロンプトに貼る。
   **固定版**（読んで納得したコミットに固定する）と**追従版**（常に `main` の最新に従う）があり、routine はカレンダーに書く権限を持つので固定版を勧める。
   時刻の既定と注意点は `nightly.md`「routine の設定」。Google カレンダー連携をコネクタに含める。
   このリポジトリに取り込まれる前（PR の段階）では clone 先に手順書が無いので、取り込まれてから登録する
6. **動作を確かめる**（下の「実機で確かめる項目」）

## 使い方の例

| 言う | 起きること |
|---|---|
| 「明日、見積書のレビュー」 | 明日に `☐ 見積書のレビュー` |
| 「見積書レビュー終わった」 | 規模（S/M/L）を聞かれ、答えると `☑` になり日付が今日に動く |
| 「繰越が多いもの」 | 繰越回数が多い `☐` の一覧と、それぞれの繰越回数・初回の予定日 |
| 「○○はやらない」 | 確認のあと `✖`（消さない） |
| 「今年の完了を集計」 | 完了数・規模別・繰越率・中止を表で |

## 設計の決定

規則の定義は `conventions.md` にあり、ここは「なぜそう決めたか」だけ。

| 決定 | 理由 |
|---|---|
| カレンダーは 1 本、状態は題名の接頭辞 | 状態ごとにカレンダーを分けると、連携ツールに「移動」が無いため削除＋再作成になり、ID と履歴が失われる。接頭辞なら 1 回の更新で済み、他の端末でも状態が読める |
| 未完了にも接頭辞（`☐`）を付ける | 既存カレンダーに通常の終日予定（休暇など）が混在する。印の無い予定を誤って繰り越さない |
| タスクは 1 色（既定は灰色）で作り、状態では色を変えない | 通常予定との見分けを一目でつけるため。状態は接頭辞 1 本で表すと決めたので、色を状態に使うと定義が 2 か所になり、夜間処理が色の保守まで負う |
| 繰越は完全自動、通知なし | 繰越は可逆で、人の判断を待つ価値がない。routine は「質問して待つ」ができないので、事後に窓口で直す設計が素直 |
| 保留の状態は持たない。未完了は上限なく繰り越し続ける | 保留（⏸）を月末日へ集める運用は、実際の見直しの周期と合わず、保留が過去の日付に取り残された。「今日の一覧に居続ける」ほうが見直しを忘れない。繰越回数は残るので、長く残っているものは「繰越が多いもの」で拾える（0.2.0 で ⏸ を廃止） |
| 中止は削除ではなく `✖` | 「手を広げすぎた度合い」を数えるため。削除は入力ミスの訂正用 |
| 完了日に日付を動かし、初回の予定日は `planned` に残す | 「この日にこれをやった」の記録と、「予定からどれだけずれたか」の両方を後から出すため |
| 完了時に規模 S/M/L を必須にする | 自由文だけだと集計できない。一言メモは任意にして完了操作を重くしない |
| 期限は `⚠`（近い）と `‼`（超過）の 2 段階、期限超過で中止にはしない | 超過は「遅れている」であって「やらない」ではない |
| 営業日は土日と日本の祝日を飛ばし、非営業日は `carried` を加算しない | 週末に 5 件並ぶのは無意味。繰越回数が週末で不当に進まない |
| 設定はカレンダーの説明欄に 1 行 | データと同じ場所にあるので、窓口・routine・別の PC で同じ読み方になり、二重管理が無い。routine の本文に個人の値を書かずに済む |
| routine の本文はポインタ | 手順の実体を版管理下に置く。アカウント側に置くと「なぜこの挙動か」が履歴から消える。実行時に取得して従う形なので、固定版を既定に勧める |

## 受け入れている制約（v1）

- **完了日は報告した日**。前日の作業を翌朝「終わった」と言えば日付がずれる。「昨日終わった」と言えばその日になる
- **繰越回数は「処理が走った営業日の数」**。routine が止まった日や非営業日は加算されない
- 画面から接頭辞を消した・規約外の書き方にした予定は、黙ってタスクでなくなる（中止数を過小評価しうる）
- 夜間処理が止まっても通知は来ない。窓口で「過去に残っている未完了」を聞けば分かる
- 中止の期間帰属は予定の日付（繰越後の最後の日付）であって、中止した日ではない
- 読む範囲は過去 2 年〜未来 1 年。それより古い置き去りは窓口で範囲を広げて探す

## 範囲外（v1）

- 家庭のタスク、タグや分類、複数カレンダーの横断
- 時間指定のタスク、繰り返しタスク
- 通知・リマインド、他人との共有
- 完了・中止を未完了に戻す操作
- 自動テスト（eval）。まず実機で動かし、痛みが出た箇所から足す

## 実機で確かめる項目

自動テストは v1 に無いので、これが唯一の検証。規約の分岐ごとに 1 件ずつ。

- [ ] 前提: カレンダー一覧の取得で**説明欄が読める**（設定行の検出が成り立つ）。Claude Code の連携では読めることを確認済み。claude.ai アプリと routine でも確かめる
- [ ] 窓口: 「明日、○○」で `☐` の終日予定が対象カレンダーに作られ（＝編集権限で接続できている）、設定行の色（既定は灰色）が付いている
- [ ] 窓口: 完了で規模を聞かれ、`☑`・完了日・`impact:` が揃う。「昨日終わった」で完了日が昨日になる
- [ ] 窓口: 完了・中止の各遷移で期限マークが外れ、中止・削除だけ確認を求められる
- [ ] 夜間処理（手元・営業日に）: 過去日付の `☐` 2 件（1 件は属性行なし、1 件は `carried: 2`）を置いて `nightly.md` を手動実行し、前者が次の営業日へ `carried: 1`、後者も次の営業日へ `carried: 3`（保留にならない）
- [ ] 夜間処理: 金曜（または祝前日）の実行で、土日祝を飛ばした営業日に移り、非営業日の実行では `carried` が増えない
- [ ] 夜間処理: 同じ日に 2 回実行しても結果が変わらない
- [ ] 夜間処理: 接頭辞なしの終日予定（休暇など）・繰り返し予定・参加者付きの予定に一切触れていない
- [ ] 夜間処理（routine）: 翌朝、手元と同じ結果が自動で出ている。routine から Google カレンダー連携が実際に動くことの確認はここ
- [ ] 集計: 1 回走らせ、件数が手で数えた結果と一致する
- [ ] 2 台目の環境（別アカウント）でも、設定行を書いたカレンダーが対象として認識される
